# HIT-94 — переиспользование TLS для ClickUp GET

Принятый HIT-93 открывал TCP и выполнял TLS handshake для каждого чтения известного ID.
Адаптер DeliveryQuery переиспользует соединения одного настроенного HTTPS origin.
Базу и кандидата сравнили с одинаковыми QueryService, TargetReader, VerifyTarget,
проверками допуска и синтетическими данными. Порядок серий A → B → B → A помогает
заметить дрейф задержек между прогонами. A — принятый код HIT-93, B — финальный код HIT-94.

## Поведение и границы

Пул на один QueryService допускает до восьми одновременных аренд и до четырёх
простаивающих соединений. Idle-соединения закрываются через 15 секунд. Одно TLS
соединение переиспользуется не дольше минуты и срока серверного сертификата.
Перед повторным использованием проверяется, что idle-сокет не закрыт и не содержит
неожиданных данных. Если idle-сокет непригоден, новое подключение возможно до
отправки GET, без повтора уже начатого HTTP-запроса.

Каждый запрос заново получает текущие полномочия и credential, проверяет сохранённую
identity и epoch, а затем проверяет и расходует общий бюджет по fingerprint.
Проверки и запись GET остаются внутри actual-start gate. Приём ответа остаётся за
его пределами. Перед сохранением наблюдения снова проверяются gate и полномочия.
Пул хранит только соединения, привязанные к origin. Авторизации, ответы и наблюдения
проверяются заново на каждом вызове.

В пул возвращаются соединения с полностью прочитанным, корректно разобранным
ответом HTTP/1.1 200 по тому же native task ID, пригодным для keep-alive. При отказе,
redirect, 429, отмене, timeout, ошибке JSON или превышении размера сокет закрывается.
Повтор на ошибке записи или чтения не выполняется. ClickUp применяет лимиты на токен,
и при HTTP 429 сообщает `X-RateLimit-Limit`, `X-RateLimit-Remaining` и
`X-RateLimit-Reset`. Ответ с `Retry-After` также завершается без повторной отправки.
См. [ClickUp Rate Limits](https://developer.clickup.com/docs/rate-limits).

Пределы пула управляют ресурсами транспорта. Они не пересматривают квоты ClickUp
или правила общего credential_budget. Реализация ClickUp create, отправка наблюдений
в Processing, исходный SQL и OAS остались прежними.

## Проверка и воспроизведение

- A: код `0914c3cbdaa82b01b15231d39ceffcec983eea7d`, ветка с исходным стендом
  `9aaf5f88dbc8eb4a511a8fafa0160d79d5e1f9b8`. Второй SHA добавляет только стенд.
- B: код `28d9541cebb280f80de14f32df2f3bffeb8d7cce`.
- В каждой серии на сценарий пять повторов, 16 GET прогрева и 96 измеряемых GET
  в повторе. После прогрева TCP считаются на сервере по состоянию `StateNew`.
- На каждом SHA из `services/delivery` запустить
  `pwsh -NoProfile -File tests/run_hit91.ps1 -ReadbackBenchmark`. Полную проверку
  кандидата запустить командой `pwsh -NoProfile -File tests/run_hit91.ps1`.
- Среда: Intel Core i5-9300H @ 2.40 GHz, 8 логических CPU и 8053120 kB доступной
  памяти по `/proc`, Linux amd64 WSL2, Go 1.27.2, Docker 29.3.1,
  PostgreSQL 18.7 Alpine с fsync, full_page_writes и synchronous_commit.
  Сырые протоколы содержат точные digest образов, команды и измерения.
- Race-тесты проверили совпадающие значимые поля TaskObservation на новом
  и переиспользованном TLS, запрет старого epoch после barrier, общий бюджет
  двух workspace, предел пула и закрытие idle/ошибочных соединений.
  Проверены redirect, 403, 429, malformed, oversize, timeout, reset,
  отмена перед записью и прежние отрицательные сценарии readback.

## Результаты

После прогрева в 20 повторах успешных GET открыто **1920 TCP-соединений на A и 10 на B**. Сокращение составило **99,48%**. По отдельным сравнениям A/B и B/A результат одинаковый, 960 против 5. При concurrency 1 после прогрева новых TCP не было. При concurrency 4 открывалось по одному на 96 GET. Для HTTP 429 в обеих версиях было по 96.

Разброс стенда не позволяет приписать изменения задержек одному транспорту. Подтверждённый выигрыш относится к числу новых соединений.

Обе серии каждого варианта сохранены в [сырых измерениях](../evidence/HIT-94/measurements.txt)

[Протокол корректности](../evidence/HIT-94/verification.txt) содержит полный прогон
`go test -v -race -count=1 ./...` и `go vet ./...`.

Замеры относятся к локальному стенду с синтетическими данными. Они не устанавливают
latency для рабочего ClickUp, готовность развёртывания или лимиты всего MVP.
