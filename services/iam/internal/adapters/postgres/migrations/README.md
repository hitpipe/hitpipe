# IAM: установка схемы и проверка защиты данных — HIT-81

Здесь находится отдельная миграция базы IAM. Она создаёт согласованные таблицы,
ограничения, права и правила изоляции рабочих пространств. Прикладной процесс IAM
её не запускает и не получает прав владельца схемы.

## Одна команда для проверки

Из корня репозитория, с Go 1.27.2 в PATH и доступным Docker:

```sh
python3 services/iam/tools/check_iam_schema.py --evidence-dir /tmp/hit81-check
```

Каталог результата должен отсутствовать или быть пустым. Для повторной проверки
укажите новый каталог: предыдущий протокол не перезаписывается. Можно передать
`--go /полный/путь/к/go`. Потребуется не менее 512 МиБ свободного места сверх уже
имеющегося образа. Это небольшая изолированная проверка компонента, а не стенд всего
продукта и не измерение его производительности.

Запуск создаёт собственный временный контейнер и базу с синтетическими данными,
открывает PostgreSQL только на `127.0.0.1` и игнорирует внешние переменные
`HITPIPE_IAM_*`. Ресурсы ограничены: 256 МиБ памяти, 0,5 CPU, данные в tmpfs.
Сначала выполняются административная подготовка ролей, миграция и её повтор;
затем тесты Go, интеграционные тесты с поиском гонок, `go vet` и сборка.
Контейнер и его сеть удаляются даже при обычной ошибке проверки. Аварийное
завершение самого процесса/хоста может потребовать удалить оставшийся контейнер
`hit81-pg-*` и связанную с ним сеть после проверки, что запуск больше не работает.
Ни один существующий контейнер или рабочая база не используются.

Старое имя `check_postgres_session_lookup.py` оставлено для совместимости CI;
оно вызывает тот же полный проход IAM. Старые отчёты HIT-68 остаются историей.

## Почему нужны разные роли

`bootstrap_roles.sql` — отдельный административный шаг **в своей базе IAM**.
Он создаёт четыре групповые роли без возможности входа: `hp_iam_migrator`,
`hp_iam_app`, `hp_iam_worker`, `hp_iam_purge`. Небезопасные существующие роли и
членства вызывают отказ. Подготовка не выдаёт прикладным ролям права мигратора
или удаления. Только мигратору разрешено создавать собственную схему в этой базе.

Администратор отдельно подготавливает входы и их секреты. Каждый вход наследует
только свою группу. Миграционный вход принимает роль `hp_iam_migrator`, например
через параметр подключения `options=-c role=hp_iam_migrator`. Затем отдельный
процесс `cmd/iam-migrate` читает `HITPIPE_IAM_MIGRATOR_DSN` из окружения. Он не
выводит строку подключения и не создаёт роли. Проверочный запуск выполняет эти
шаги сам, используя только одноразовые входы без настоящих секретов.

При первом запуске ответ содержит `state: installed`, `version: 1` и хеш SQL.
При повторном — `state: already_installed`: таблицы и время установки не
пересоздаются. Параллельные миграторы сериализуются блокировкой в своей базе.
Миграция исполняет собственные `BEGIN/COMMIT` исходного SQL; запуск внутри уже
открытой транзакции запрещён. Ошибка SQL откатывает незавершённое создание схемы.
Неизвестная/неполная версия, чужой владелец, изменённые правила доступа и опасные
исходные права вызывают отказ без автоматического удаления или ремонта данных.
Проверка повторного запуска охватывает версию, владельцев, таблицы и права;
это не универсальная сверка всех возможных изменений структуры столбцов/индексов.

## Что проверяют тесты

Для десяти таблиц с `workspace_id` проверяются права и RLS — дополнительная
защита строк: без выбранной рабочей области данные не видны, чужая запись
отклоняется, `SET LOCAL` действует только внутри своей транзакции. Владелец схемы
также подчиняется принудительной RLS. Приложению и обработчику запрещено менять
или удалять уже записанные `audit_minimal` и `command_receipts`.

`principals`, `sessions`, `runtime_registry`, `revocations` и
`revocation_participants` имеют отдельную общую границу IAM. Наличие
`hp.workspace_id` не превращает доступ к ним в бизнес-полномочие пользователя.
`job_index` доступен обработчику и роли очистки, но не приложению. Реальные входы
проверяются отдельно от суперпользовательского соединения подготовки данных.

Проверяются уникальность внешней личности, хеша сессии и внешнего подключения,
согласованные SQL-ограничения времени, сохранение commit после нового соединения,
отсутствие частичного результата после rollback и атомарность сбоя самой миграции.
Сохранены команды, коды завершения, версии, хеши и вывод каждого этапа.

## Граница результата

Готовность миграции и проверки схемы в одноразовой базе не означает готовность
входа пользователя, выдачи сессий, бизнес-полномочий, распределённого отзыва или
развёртывания. Эти механизмы остаются отдельными задачами. RLS не заменяет проверку
текущих полномочий: сам сервис способен выбрать значение своего SQL-параметра.
Согласованная схема не гарантирует правила времени и связности, которые в ней
не выражены ограничениями; их должен проверять соответствующий прикладной код.
