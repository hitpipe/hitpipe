# HIT-154 · Реестр подтверждений удаления содержимого дела

Процедура IAM/Platform выпускает и хранит подтверждение владельца. Она не удаляет
содержимое и не добавляет пользовательский API. HIT-148 отвечает за применение
решения: принадлежность версий, безопасную очистку, живые общие ссылки,
сохранение обязательных метаданных и защиту от повторных внешних действий.
Контракты сторон сверяются по [закреплённой поправке](https://github.com/hitpipe/project-os/blob/0dc25affc7cb19b1a74a16d80b93eac0d9961c05/contracts/hitpipe/case-deletion-2026-11-22/CASE_DELETION_AUTHORITY_RU.md).

## Источник и полномочия

- В Linux TEST выделите издателю отдельный абсолютный каталог, принадлежащий
  только ему, с правами `0700`. `filestore/casedeletion.Initialize` принимает
  только пустой каталог и начальное состояние из `app.NewState("test")`.
  Для обычного запуска используйте `Open`: он не создаёт потерянный реестр.
  `registry.lock` и `registry.json` (оба `0600`) остаются у издателя.
- Каталог реестра, файл блокировки и конфигурация доверия должны быть вне
  PostgreSQL, каталога содержимого и набора, из которого восстанавливается
  Processing. Не монтируйте каталог реестра в Processing. Не подменяйте файлы
  вручную: запись синхронизируется, публикуется атомарно и ограждена общим
  межпроцессным `flock`. При потере источника, смене его идентичности, повреждении
  или неопределённом завершении записи область остаётся закрытой; пустой
  реестр не используется вместо утраченного.
- Соберите `app.Registry` через `app.New` с ключом подписи издателя, его
  идентификатором, окружением и идентификатором выделенного Processing.
  `postgres/casedeletion.New` использует существующие права IAM и доверенные часы.
  Он проверяет сессию, текущую роль `OWNER`, активность пространства и запреты
  из IAM. Служебный сертификат, роль оператора и права чтения не дают права
  подтвердить удаление. Издатель обслуживает реестр; решение подтверждает сам
  действующий владелец через доверенный локальный интерфейс процедуры.

## Выпуск, применение и квитанция

1. Издатель подготавливает пространство через `ProvisionWorkspace`. Вызов
   `Prepare` сверяет предложенную область через `TargetAuthority`: одно дело,
   его пространство и точные версии `CASE_CONTEXT` / `HISTORY`. Он возвращает
   подписанное предложение `offer-v1`, но ничего не записывает. Покажите
   владельцу всё предложение: дело, версии и то минимальное состояние дела,
   которое сохранится.
2. Только после отдельного явного подтверждения владельца вызовите `Confirm` с
   его действующей сессией, неизменённым предложением и привязанным к нему
   `ConfirmationCode`. IAM удерживает проверенные записи владельца и исключает
   конкурирующую запись запрета; при новом подтверждении затем проверяются
   точные версии и только после этого берётся блокировка записи реестра.
   Вложенные вызовы не должны менять порядок этих блокировок. Callback записи
   выполняется синхронно; он не должен ждать пользовательского ввода или
   повторно вызывать реестр. Подмена области и чужая роль не создают запись.
3. `CONFIRMED` можно отменить через `Cancel` действующим владельцем до начала
   применения. Издатель сохраняет `APPLYING` через `StartApplying` до любых
   действий Processing. Повтор использует тот же `deletion_id` и ровно те же
   версии; до действительной квитанции `APPLYING` остаётся в реестре.
4. Processing посылает квитанцию только после проверки устойчивого применения
   решения. Издатель сверяет её через `ApplicationAuthority.WithApplied`,
   затем проверяет область и поколение ещё раз под блокировкой записи реестра
   при публикации `APPLIED`. Повтор той же квитанции допустим; иной результат для того же решения,
   чужая область или предыдущие поколение и ревизия отклоняются.

У издателя остаётся частное доказательство проверки владельца: идентификатор,
время и подпись предложения `offer-v1`, а также подпись `confirmation-v1`
фактического подтверждения, связанная с предложением, областью и временем.
Processing получает только контрольную ссылку `confirmation_ref`, без самого
доказательства. Сессии, ключи, контакты, тексты и тела содержимого не включаются в
реестр, выдачу и протоколы проверки.

## Закрытый обмен с Processing

Подключайте `http/casedeletion.NewServer` только к выделенному приватному
слушателю синтетического стенда. TLS 1.3 проверяет отдельный доверенный CA,
DNS SAN и точный отпечаток DER сертификата Processing. Издатель связывает
сертификат со служебной идентичностью и списком пространств в своей настройке.
Идентичность не берётся из заголовка или тела. Клиент `NewClient` проверяет CA,
имя узла и точный отпечаток сертификата издателя, не следует перенаправлениям
и не повторяет отправку квитанции автоматически.

| Маршрут | Смысл и формат |
| --- | --- |
| `GET /internal/maintenance/v1/case-deletion/snapshot?workspace_id=…&generation=…` | Только чтение, полный снимок не более 4 МиБ. JSON: `payload` (версия схемы, окружение, издатель, пространство, поколение, ревизия, `full:true`, массив `decisions`) и подпись Ed25519 `signature` в Base64. Решение содержит `deletion_id`, действие, издателя, точную `scope` со списком `class` / `version_id`, `scope_digest`, время, ссылку подтверждения, состояние, `apply_generation`, `apply_revision`, `applying_at` и минимальные квитанции текущего поколения. |
| `POST /internal/maintenance/v1/case-deletion/receipt` | Только JSON до 8 КиБ: `environment`, `workspace_id`, `deletion_id`, `scope_digest`, `generation`, `revision`, `applied_at`, `application_ref`. Код `204` означает принятие или точный повтор. `revision` — `apply_revision` решения, а не новая ревизия всего снимка; `application_ref` — SHA-256 доверенного доказательства устойчивого применения. |

У Processing нет методов создания, отмены, смены поколения или установки
состояния. Ревизия снимка монотонно растёт отдельно для каждого пространства.
Внутренний файл также хранит общий счётчик публикаций. Изменение соседнего
пространства не делает снимок этого пространства устаревшим.

## Восстановление и допуск к данным

1. Восстановленный экземпляр начинает в `CLOSED`. Доверенный локальный
   координатор издателя вызывает `AdvanceGeneration` со старым и следующим
   поколениями. Ранее применявшиеся решения снова становятся `APPLYING` с тем
   же идентификатором и версиями; старые квитанции остаются только у издателя.
2. Processing проверяет подпись через `VerifySnapshot` с закреплённым ключом
   издателя и ожидаемыми окружением, пространством и поколением. Переисполняет
   сохраняющие силу решения для восстановленной копии и возвращает проверяемые
   квитанции. Подлинный полный снимок с `decisions:[]` означает отсутствие
   решений; отсутствие файла, необъявленная область, неполный снимок, другой
   издатель или недоступность источника никогда не означают то же самое.
3. Перед открытием доверенный локальный координатор передаёт проверенный
   снимок в `WithCurrent`. Он сравнивает его с живым источником и требует,
   чтобы все решения были применены или отменены. Переход `CLOSED → OPEN`
   выполняется синхронно под общей блокировкой реестра, пока публикации
   исключены. Никакая удалённая операция GET не открывает данные: подлинная
   старая копия не доказывает текущую ревизию. При конфликте, ошибке или
   изменении ревизии нужно заново сверить источник и оставить область закрытой
   до успешной проверки.

## Воспроизводимый TEST

Из чистого корня рабочей копии на Linux с Bash, Go 1.27.2, Docker, Python 3
и `jq` выполните:

```bash
set -euo pipefail
test -z "$(git status --porcelain)"
sha="$(git rev-parse HEAD)"
out="$(mktemp -d)"
printf '%s\n' "$sha" > "$out/source-commit.txt"
python3 services/iam/tools/check_authorization.py --evidence-dir "$out/iam" | tee "$out/driver.log"
jq -e --arg sha "$sha" '.source_commit == $sha and .state == "PASSED" and .postgres_version == "18.7"' "$out/iam/verification.json"
grep '^--- PASS: TestPostgresCaseDeletionQualification ' "$out/iam/postgres-race.log"
```

Драйвер поднимает отдельный контейнер PostgreSQL закреплённого образа, гоняет
прежние проверки IAM, тесты с детектором гонок, `vet` и сборку. Интеграционный
сценарий `TestPostgresCaseDeletionQualification` в
`services/iam/internal/adapters/composition/casedeletion` использует два
синтетических пространства и проверяет закрытое восстановление с сохранением
независимого реестра. Сохраняются версии, SHA, команды, коды возврата и журналы
из каталога `$out`. Эти материалы квалифицируют только тестовый контур и
соглашение интеграции для HIT-148.
