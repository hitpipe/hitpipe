# IAM для сквозной проверки HIT-146

Сборка включает принятые результаты HIT-115 и HIT-116. Для стенда нужны реальные PostgreSQL 18.7 и два процесса с доверенными сертификатами. Штатные операции регистрации и применения барьера описаны в действующем OpenAPI.

## Идентичность экземпляра

Доверенный запуск заранее закрепляет `service`, `runtime_id`, `generation`, свежий одноразовый `boot_id` и отпечаток исходящего клиентского сертификата. IAM получает эту запись в `runtimeaccess.Binding`. Тот же `boot_id` нужно передать единственному экземпляру Processing. В ветке эксперимента HIT-146 Processing генерирует его внутри `runtime.New`. Для стенда владелец Processing должен подключить доверенный ввод при запуске соответствующей загрузки. При замене действующего экземпляра требуется проверенное ограждение старого boot и более новое поколение. Само предъявление сертификата или отсутствие ответа прежнего экземпляра эти условия не подтверждает.

## Регистрация и открытие

1. Приватный слушатель IAM принимает точную mTLS-регистрацию, пока локальная заслонка IAM ещё закрыта. Первый запрос Processing сохраняет состояние `SYNCING`.
2. После регистрации всех участников IAM выполняет свой обычный `Start`. Он сверяет реестр, применяет актуальный снимок к собственной заслонке и открывается.
3. Следующий запрос регистрации с той же точной идентичностью получает свежий `OPEN`, если состав реестра полный. Новый снимок и допуск фиксируются под замком реестра. Processing применяет снимок к локальной заслонке своего boot. Защищённый старт остаётся закрытым до успешного применения.
4. Ответ `OPEN` разрешает применить выданный снимок. Факт открытия удалённого экземпляра проверяется в самом процессе. ACK отзыва приходит отдельным запросом к защищённому порту после завершения прежних секций старта.

Недоступная PostgreSQL, неполный реестр и неизвестный или незакреплённый boot сохраняют закрытый отказ. Точный повтор при действующем состоянии может получить новый снимок без создания второго экземпляра.

## Управляющий сертификат

Координатор стенда передаёт в `revocation.NewClientWithControlBindings` только данные доверенного запуска. Для каждого участника `ControlBinding` содержит точный `Identity` (runtime, boot, generation), `RegistrationFingerprint` клиентского сертификата, `ControlFingerprint` отдельного серверного сертификата и HTTPS `Origin` приватного порта 9443. Для одного экземпляра с двумя сертификатами фиксируются оба отпечатка. Координатор проверяет, что привязка относится к зарегистрированному участнику, сверяет TLS цепочку, имя и точный control-отпечаток, затем проверяет поля ACK. Происхождение адреса и отпечатков устанавливает составитель стенда.

Собственный IAM слушает барьер через `privateiam.Server.ControlHandler` с существующей TLS-конфигурацией `revocation.ServerTLS`. Этот обработчик использует ту же заслонку, что и авторизация IAM. На 8443 остаются зарегистрированные бизнес-маршруты, а обработчик барьера монтируется только на 9443.

## Проверка HIT-146

Собрать стенд с точными SHA IAM и Processing. Проверить закрытый первый запуск, отказ чужому boot и сертификату, полезный вызов после применения снимка, удерживаемый начатый запрос, реальный ACK полного списка и отказ старой эпохе. Снять времена и сравнить с пятью секундами. Отсутствие ACK отдельно проверяется как отрицательный сценарий.
