# Создание сессии IAM · HIT-83

После успешно проверенного входа IAM может создать случайный секрет сессии и
сохранить пользователя вместе с сессией одной транзакцией. Пользователь определяется
парой `(issuer, subject)` — провайдером входа и его внутренним идентификатором.
Совпадение email не объединяет разных пользователей.

## Из каких частей состоит результат

- `internal/application/issuesession`: проверяет подтверждение входа, доверенное
  время и разрешение IAM на создание сессии; создаёт секреты и возвращает результат
  только после подтверждённого сохранения и повторной проверки условий.
- `internal/adapters/postgres/sessionissuer`: использует переданный владельцем IAM
  пул PostgreSQL, проверяет прикладную роль, атомарно получает или создаёт пользователя
  и добавляет сессию в существующую схему HIT-81.
- Существующие `sessionpolicy`, `authenticatesession` и оптимизированный
  `postgres/sessionlookup` из HIT-68/82 читают новую сессию без изменения своего
  интерфейса. Схема SQL и правила доступа сохранены.

## Что требуется для подключения

Конструктор приложения требует четыре явно заданных подключения: проверяющий
одноразовое подтверждение входа (`Verifier`), доверенные часы (`Clock`), проверку
разрешения IAM (`IssuanceGuard`) и хранилище (`Store`). Отсутствующее подключение,
неизвестное разрешение, необходимость ещё не реализованной ротации или незавершённый
отзыв закрывают создание сессии. Сам по себе успешный вход не даёт прав на рабочие
области и бизнес-операции.

Проверяющий обязан проверить провайдера, подпись и связь с попыткой входа, затем
атомарно погасить подтверждение один раз. Приложение дополнительно требует
подтверждённый email и действительную попытку длительностью не более 10 минут.
После сохранения проверка IAM должна по-прежнему разрешать выдачу с той же эпохой
безопасности. Реальные подключения этого уровня здесь не подменяются разрешающими
заглушками: управляемые реализации существуют только в тестах.

Сроки задаются обязательным `Policy{AbsoluteLifetime, IdleLifetime}`. Значения по
умолчанию отсутствуют. Приложение проверяет
`0 < IdleLifetime <= AbsoluteLifetime <= 24 часа`; верхняя граница сохраняет правило
существующей `sessionpolicy`. Точный принятый пакет MVP не задаёт новые численные
значения обоих сроков, поэтому компонент их не придумывает. Значения 8 и 24 часа в
тестах являются явно заданными тестовыми входами. Рабочие значения требуется явно
задать при будущем подключении входа.

Пул остаётся собственностью вызывающего кода. Для него задаётся не более 10
соединений; в проверках используется 5. Операция сохранения ограничена двумя
секундами, включая получение соединения, блокировки и подтверждение транзакции.
Прикладной логин наследует только `hp_iam_app`; владелец схемы, суперпользователь,
worker и purge для этого подключения не подходят.

## Секреты и ошибки

Каждый секрет сессии и CSRF создаётся из 32 байт `crypto/rand` и кодируется в 43
символа Base64URL без дополнения. SQL получает только SHA-256 точных закодированных
значений. Это совместимо с существующим `sessionlookup.Reference`.

Секреты результата скрыты при обычном форматировании и JSON-сериализации. Будущий
транспорт получает значение только явным `Reveal()`. Метаданные cookie фиксируют
`__Host-hp_session`, `Secure`, `HttpOnly`, `Path=/`, отсутствие `Domain` и
`SameSite=Lax`. HTTP-ответ здесь не создаётся; доставку и проверку CSRF подключает
будущий транспорт. Восстановить CSRF из сохранённого хеша невозможно.

Отмена, отказ часов, источника случайности, проверяющего или базы не возвращают
успешный результат с секретами. Подтверждение входа не используется повторно после
ошибки сохранения. Если ответ на COMMIT потерян либо окончательная проверка после
COMMIT не прошла, строка уже может находиться в базе: компонент не заявляет откат и
не повторяет запись вслепую. Секрет такой строки не выдаётся вызывающему коду.

Отключённый пользователь и существующий незавершённый отзыв его сессии дают отказ.
Адаптер не меняет эпохи, отметки отзыва или состояние его координатора. Полная
согласованность распределённого отзыва требует действительного рабочего механизма
IAM; два чтения тестового разрешения его не реализуют.

## Как проверить

Из корня репозитория, с принятой Go 1.27.2 и доступным Docker:

```sh
python3 services/iam/tools/check_session_issuance.py --evidence-dir /tmp/hit83-check
```

Если Go отсутствует в PATH, укажите `--go /путь/к/go`. Скрипт принимает только
одноразовую локальную базу и сам создаёт и удаляет контейнер и сеть. Используется
точный согласованный образ PostgreSQL 18.7 Alpine. Старые протоколы не
перезаписываются: каталог вывода должен быть пустым.

Проверяются обычные тесты, настоящая PostgreSQL вместе с `-race`, `go vet` и сборка.
Пропуск обязательных проверок создания сессии не считается успехом. Для каждой
команды сохраняются вывод, код завершения и хеш; отдельно фиксируются версия кода,
дерево исходников, версии инструментов и удаление тестового стенда. Обычная точка
входа существующего CI также требует тесты нового компонента.

## Граница готовности

Результат HIT-83 — локальный компонент с проверенной записью в настоящую базу.
В HIT-106 остаются реальный OIDC-вход через Keycloak и его долговечные одноразовые
попытки, HTTP-подключение и согласованная рабочая конфигурация. Регистрация с
email-кодом, общий logout/rotation/revoke, бизнес-полномочия и развёртывание требуют
собственных реализаций. Публичный сервер и рабочие учётные записи этой задачей не
меняются.
