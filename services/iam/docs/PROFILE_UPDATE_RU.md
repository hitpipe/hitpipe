# HIT-125 · сохранение собственного профиля

Приватный IAM:8443 принимает PATCH `/api/v1/profile` от BFF по TLS 1.3 с
клиентским сертификатом. IAM сверяет принятый DNS SAN, отпечаток сертификата
и текущие регистрации BFF и IAM. Тот же шлюз HIT-115 защищает SQL и начало
ответа. Пользователь определяется по сохранённой сессии. CSRF сравнивается
по SHA-256 исходного значения, которое выдал issuer HIT-83. Данные тела и
заголовков не назначают пользователя.

PATCH принимает `command`, `display_name` и `timezone` по принятому
`ProfileUpdate`. Поля имеют прежние пределы 1–120 и 1–80 символов. UUID в
`X-Request-ID` должен совпадать с `command.request_id`. Для изменения
обязателен `command.expected_revision`. Если передан `If-Match`, BFF
передаёт сильный тег с той же десятичной ревизией, например `"4"`.
Точный UUID команды и RFC 8785 SHA-256 тела определяют повтор.

Перед записью IAM читает текущий проверенный файл и сверяет ревизию.
Новое полное содержимое получает прежний `user_id` и следующую ревизию.
Владелец создаёт новый непрозрачный файл UUIDv4 в формате HIT-85, синхронизирует
файл, атомарно переименовывает и синхронизирует каталог. Затем PostgreSQL
атомарно меняет пару `principals.profile_content_ref` и `profile_digest`
только у текущего владельца с прежней точной парой. GET HIT-85 читает лишь
целую версию, на которую указывает БД. Смена email, ролей и принадлежности
к рабочим областям вне этого метода.

## Результат команды и условия запуска

В закреплённом DDL квитанции требуют `workspace_id` из tenant-области.
У собственного профиля нет workspace и нет глобального счётчика или
квитанции в `principals`. Принятый механизм долговременного хранения таких
команд в просмотренных источниках отсутствует. Поэтому рабочая композиция
требует явно предоставленного `CommandAuthority`. При его отсутствии
PATCH возвращает `503`, а прежний защищённый GET работает.

Изолированный стенд предоставляет отдельный **тестовый** файловый журнал.
Он удерживает исключительный доступ по действительному principal, пишет
подготовленное намерение до SQL и подтверждает ровно этот результат после
известного commit. Хранилище переживает переоткрытие и проверяется отдельным
процессом. Оно показывает один способ проверяемой композиции. Эксплуатационное
согласование, график очистки и распределённое хранилище квитанций здесь
не вводятся.

Повтор с тем же телом проверяет текущее право и под блокировкой сверяет
действительный SQL-указатель с подготовленным намерением. Точная новая пара
подтверждает уже записанный результат и исключает повторную запись. Точная
прежняя пара после нового захвата SQL-строки позволяет продолжить то же
намерение после установленного отката. Другая пара оставляет исход
неподтверждённым, а уже подтверждённый, затем заменённый результат получает
`412`. Отличающееся тело для прежнего UUID получает `409`. Потеря
подтверждения SQL или журнала возвращает `503`, пока результат нельзя
установить. Сырой токен сессии и CSRF не записываются в журналы.

## Передача формы HIT-110

Примеры ниже используют только синтетический UUID, имя и часовой пояс.
Сессия и CSRF поступают от штатного входа после его подключения к BFF.
Пример отправляется между BFF и IAM, за пользовательский HTTP-вызов
отвечает BFF.

```http
PATCH /api/v1/profile HTTP/1.1
Content-Type: application/json
X-HitPipe-Session: <opaque-session>
X-CSRF-Token: <issuer-csrf>
X-Request-ID: 6ba7b810-9dad-41d1-80b4-00c04fd430c8
If-Match: "4"

{"command":{"request_id":"6ba7b810-9dad-41d1-80b4-00c04fd430c8","expected_revision":4},"display_name":"Тестовый профиль","timezone":"Europe/Moscow"}
```

Успех возвращает HTTP `200` и полный `Profile`. Следующий GET с той же
действующей сессией показывает сохранённые значения и ревизию 5.

```json
{"user_id":"60a92117-41d4-4b02-95e7-187d85e07817","display_name":"Тестовый профиль","timezone":"Europe/Moscow","revision":5}
```

Новый UUID со старой `expected_revision: 4` получает `412`. Использование
чужого токена CSRF с этой сессией получает `403`. Отозванная или истёкшая
сессия получает `401`, допустимая ошибка доступности зависимостей — `503`.
После `412` форма должна обновить профиль и дать участнику сверить изменения.
Вход, GET session, доставка CSRF, logout и рабочее подключение BFF остаются
отдельными частями интеграции.
