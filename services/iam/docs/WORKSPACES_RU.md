# HIT-124 · приватный API рабочих областей IAM

`GET /api/v1/workspaces` и `POST /api/v1/workspaces` доступны компоненту BFF
на частном адресе IAM:8443. `ListenWorkspaces` использует TLS 1.3, клиентский
сертификат из закреплённой CA и точную пару DNS SAN/отпечаток из инвентаря
экземпляров. IAM и BFF должны иметь действующие регистрации своих конкретных
загрузок и поколений. Оба метода используют тот же шлюз начала работы, что
существующий IAM authorize из HIT-115. Старый `Listen` сохраняет свой набор
маршрутов.

BFF передаёт исходную сессию в `X-HitPipe-Session`. Для POST он также передаёт
исходный `X-CSRF-Token`, SHA-256 которого сравнивается с `csrf_hash` этой сессии.
`X-Request-ID` связывает диагностику с запросом. Долговременную идентичность
команды задаёт отдельный UUID `command.request_id` и SHA-256 канонического
тела JSON (RFC 8785). Например, тестовый запрос создания имеет такое тело:

```json
{"command":{"request_id":"472fcd63-ab4e-41ce-bac5-123456789abc"},"name":"Рабочая область"}
```

GET возвращает `200` и объект с массивом `items` до 50 элементов. У каждого
элемента есть `workspace_id`, `name`, `role`, `lifecycle`, `revision`,
`security_epoch`. Каталог нужен только для
нахождения идентификаторов. Отдельный запрос с FORCE RLS по каждой кандидатной
области читает текущую область, активное членство и сохранённое имя. Перед
началом ответа повторно сверяются сессия, доступы, версии и эпохи. Строки IAM,
защищающие эти факты, удерживаются до начала записи. У принятой таблицы
членства составной ключ, поэтому отзыв MEMBERSHIP с неразрешимым subject
закрывает затронутую область по правилу HIT-115.

POST принимает явный допуск доверенного владельца, закрепляющий действительный
`workspace_id` за текущим principal и UUID команды. Допуск должен подтверждать
владельца и публично представимое состояние `ACTIVE`. Имя и минимальный
локальный payload исходящего сообщения публикуются в файлах владельца с
непрозрачными UUIDv4, режимами 0700/0600 и синхронизацией файла и каталога.
В одной транзакции `hp_iam_app` сохраняет workspace, первое членство ACTIVE
OWNER, исходные revision/security_epoch, квитанцию, запись аудита и запись
outbox. `initial_activation_at` остаётся NULL. Активация операции требует
своего подтверждения и проверок подключений.

Установленная команда возвращает `201` и текущую допустимую проекцию той же
области. Точный повтор использует прежнюю квитанцию и непрозрачные ссылки
без новой записи. Другое каноническое тело с тем же UUID даёт `409`. Команда
создания не принимает expected_revision/If-Match для ещё отсутствующей
области (`412`). При потере подтверждения commit ответ об успехе закрыт.
Повтор допустим с тем же UUID и телом, после восстановления действительной
сессии и того же допуска. Сохранённый SQL-результат определяет исход.

## Границы квалификации

Стенд подаёт настоящую сохранённую сессию, проверяет CSRF по сохранённому
digest и использует явно заданный набор кандидатов и ограниченный onboarding
допуск. При отсутствующих источниках список и создание закрыты. Публичный
enum не позволяет выдавать `ONBOARDING`, а DDL не даёт глобальной квитанции
создания до установления действительной области. Поэтому вход без такого
допуска, внутреннее ONBOARDING, глобальный поиск команды и восстановление
допуска после его утраты остаются закрыты. В рабочем окружении требуется
долговременный источник стабильного соответствия principal/команда/область.

Рабочие GET session, доставка и ротация CSRF, logout, ввод BFF в эксплуатацию,
распределённый запуск и потребитель локального outbox не входят в эту
поставку. Удаление временных данных выполняет стенд. Рабочее обслуживание
неподтверждённых файлов должно сверять владельческие ссылки и сохранять их
до установления исхода SQL. Реальные Stripe и ClickUp не участвовали.
