# HIT-73 — проверка и нормализация подписанного события

Реализован изолированный переход от исходных подписанных байтов Stripe к принятой
схеме `NormalizedSignal`. Сигнал не подтверждает оплату, сохранение или HTTP-приём.

## Исходная база и переиспользование

Рабочая база — актуальный main `ce771d37505e7770003d0796ae932556d06b7bab`.
В его полном отслеживаемом дереве `services/intake` отсутствовал. Поиск PR по HIT-73
не нашёл готового соответствующего результата. Проверены история локальных refs,
результат HIT-58 (комментарий11303) и актуальные замечания HIT-73.

PR [№32](https://github.com/hitpipe/hitpipe/pull/32) повторно прочитан: открыт, не слит,
head `e64f4ff4310c597414f768ea705b6ceb1221e1b2`. Модуль перенесён из этой точной версии;
код и тесты AuthenticateWebhook и StripeSignature сохранены. Чужой PR и закрытые
учебные задачи не изменялись. Новая нормализация находится в
`internal/application/normalizesignal`, а не в историческом учебном отчёте.
Область поиска и версии записаны в `../../evidence/HIT-73/source-audit.json`.

## Что делает код

1. Ограничивает тело256КиБ и заголовок2048байт, делает собственную копию тела.
2. На каждой доставке вызывает существующий AuthenticateWebhook: точные байты,
   HMAC-SHA256, constant-time comparison, допуск времени300секунд, секрет только
   для явно переданного installation. Дедупликация не обходит подпись.
3. Проверяет обязательные явно переданные workspace/connection/account, известный
   test/live, поддержанную API version, тип account binding, идентификаторы и сроки
   receipt. Не генерирует ID или время первого приёма; первое время не в будущем,
   срок ещё действует, TTL не больше72часов. message_id — UUIDv4.
4. После подписи отвергает неверный JSON, дубликаты ключей (также экранированные),
   недопустимый Unicode, неизвестные имена полей на границе проекции, неправильные
   типы/отсутствующие/null обязательные поля, неизвестную версию и event type.
   Поддерживает три значения event_type из принятой схемы. async_payment_failed
   является только сигналом, не разрешением обычной финансовой оценки.
5. Проверяет event.object=event, data.object.object=checkout.session, ID и оба
   livemode. Для CONNECTED нужен совпадающий подписанный Event.account; для DIRECT
   account берётся исключительно из заранее проверенной установки, Event.account
   должен отсутствовать. Неизвестный тип подключения не даёт DIRECT по умолчанию.
   Непустой организационный Event.context удерживается: этот путь не реализован.
6. Переносит session_id из подписанного data.object.id и source_created_at только
   из data.object.created. Event.created и время получения не заменяют Session.created.
   Применено [решение HIT-78](https://hitpipe.atlassian.net/browse/HIT-78?focusedCommentId=12171).
7. Создаёт ровно14полей схемы. metadata, контакты, brief, платёжные поля и сырое тело
   не переходят в сигнал. Допустимые дополнительные поля Stripe отбрасываются;
   они не являются внутренними полями NormalizedSignal. Неизвестные имена верхних
   provider полей отвергаются; проигнорированные вложенные данные не интерпретируются.
8. Считает SHA-256 RFC8785 JCS полного сообщения без свойства message_digest.
   Используется закреплённый github.com/gowebpki/jcs v1.0.2, а не сортировка JSON.

## Договор вызывающего кода и ограничения

`Binding` — проверяемый вход от владельца установки. Содержимое webhook или браузер
не могут выступать его источником. `APIVersion` должно быть явно проверенным
поддержанным значением установки; тестовое synthetic-version не разрешает реальную
версию Stripe. Нет чтения установки, live connector, проверки текущих grants/epoch
или доверенных часов в этой задаче: соответствующие порты передаются явно.

`Receipt` передаётся владельцем identity. На повторе он обязан получить те же
message_id/receipt_id/first_received_at/expires_at из собственного устойчивого
состояния. Этот модуль сохраняет переданные значения, но без хранилища не может
доказать их прежнее сохранение или запретить вызывающему коду подменить их. Будущий
receipt/dedup adapter обязан проверять неизменность и конфликт digest атомарно.
Полученный Signal — кандидат для следующего owner slice, не durable ACK.

Рабочая копия первоначального чата с незакоммиченными отчётами сохранена; изменения
выполнены отдельно в ветке codex/HIT-73-normalize. HTTP-маршрут, база, файловое
хранилище, outbox, отправка, финансовое решение и внешние действия не добавлены.
Настоящее подключение Stripe, надёжное сохранение, успешный HTTP-ответ и работа
внешнего сервиса этими тестами не доказаны. Независимого PASS и приёмки пока нет.

## Проверки и воспроизведение

Запускать из корня репозитория:

```sh
python3 services/intake/tools/check.py --go /path/to/go1.27.2/bin/go
```

`../../evidence/HIT-73/commands.json` содержит точный проверенный SHA, состояние
дерева, версии, хеши исходников, команды и коды завершения. Рядом — исходные журналы
race/vet/build/modules. Все примеры синтетические. Включены прежние применимые тесты
модуля, новая нормализация, сверка выходного JSON с точной принятой схемой, JCS
числа/Unicode/ordering/null/duplicates, оба account scope, test/live, повтор с
поддельной подписью, неверные/отсутствующие поля, лимиты размера/длины и TTL.

CI `pr12-intake` теперь запускает эти текущие проверки модуля и сохраняет журналы,
не возобновляя академические процедуры закрытой очереди.

Закреплён Go1.27.2; контрольная сумма официального darwin-arm64 архива:
`76812b213b1b2302c978d28fa52fa92d541704b9e7d9d5db8002c50e4018c4c5`.
Известный GO-2026-6859 относится к HTTP-серверу net/http; этот модуль не содержит
HTTP-сервера. Это не квалификация безопасности будущего deployment и не основание
самостоятельно менять общий Go pin.
