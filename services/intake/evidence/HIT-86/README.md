# HIT-86 — локальный надёжный приём Intake

Прикладной метод `receivesignal.Consumer.Receive` соединяет существующую проверку
подписи и нормализацию, файловое сохранение и короткую транзакцию PostgreSQL.
Успех означает один локально сохранённый приём и запись outbox. Это не HTTP-ответ
поставщику и не подтверждение приёма Processing.

## Исходные версии и переиспользование

Проверен актуальный main `ce771d37505e7770003d0796ae932556d06b7bab`: в его дереве нет
services/intake. Jira HIT-71/73/74 прочитаны напрямую: все три «Готово». Их PR
остаются открытыми и не считаются слитыми. В собственной ветке от main использованы:

- HIT-71, PR47, `9af6ba6d1b1619d4f3df04059adc186cfaa5c01a`: миграция, роли и проверки схемы;
- HIT-73, PR65, `551399a8efeeb266f6f417a097c5cf2b6db08864`: AuthenticateWebhook, StripeSignature и normalizesignal вместе с тестами;
- HIT-74, PR66, `22a99989f1f4fb3a73747647eef98c20b508cd0c`: contentstore и его тесты.

Соответствующее готовое решение HIT-86 не найдено: проверены полный main,
история/доступные части Intake и поиск PR HIT-86. Поиск вернул нерелевантный HIT-83,
который не использован. Новая реализация находится в application/receivesignal и
adapters/postgres/receipt. Нормализатор и криптографическое ядро не переписывались.
Тип файловой ссылки вынесен в domain/contentref; старый contentstore.Ref оставлен
алиасом. Это соединение типов, без изменения файлового алгоритма.

DDL сохранён из HIT-71 без изменения, SHA256:
`0d477eac94bf5dd9a861c614b9970a7f828558ae5a7663874b62475f26247093`.
Он совпадает с текстом принятого HP-MVP-SQL-INTAKE; завершающая пустая строка перед
закрывающим Markdown fence в PERSISTENCE не является SQL-изменением. Существующие
377 проверок схемы выполняются заново как применимые тесты HIT-86; закрытые задачи
и академические gates не возобновляются. Изменён только транспорт ожидания тестового
контейнера в старом check_postgres.py: localhost TCP вместо Unix-сокета временного
стартового сервера. Состав SQL-сценариев не изменён.

## Порядок сохранения

1. Проверить явно переданные workspace/connection/account/mode/API version/epoch и
   доверенные часы; скопировать входные байты. Проверить подпись и нормализовать
   каждый приход, включая дубликат. Контекст не извлекается из неподтверждённого JSON.
2. В отдельной базе Intake получить session-level advisory lock. Он сериализует
   публикацию и очистку между экземплярами метода. Это исходная простая реализация,
   не измеренная оптимизация. Ожидание ограничено10секундами. Нет SQL-транзакции
   или row lock во время file IO. Все publisher/cleanup этого owner DB обязаны
   следовать одному протоколу. Другие сервисы и cross-service SQL не подключены.
3. Под ролью приложения в короткой транзакции SET LOCAL рабочую область и проверить
   существующее подключение: совпадают account/mode/epoch, health=READY, verified_at
   известен, revoked_at отсутствует. Прочитать приём по существующему
   UNIQUE(workspace_id,connection_id,event_id), затем закончить транзакцию.
4. Если приём уже существует, взять первоначальные ID/времена из signals/outbox,
   повторно нормализовать подписанное событие с ними и сравнить с реальными
   сохранёнными байтами. Противоречие — отказ; отсутствующий outbox/файл, EXPIRED
   или истёкший срок не дают успешный пригодный приём. Ничего не перезаписывается.
5. Для нового приёма создать UUIDv4. Одно его значение служит signal_id, receipt_id
   и message_id: это явная локальная связь существующих ключей, а не ID поставщика
   и не новая таблица. Входящая уникальность остаётся tuple Stripe event ID.
   Первое время фиксируется из первого доверенного чтения часов в UTC с точностью
   секунды; это сохраняемая точность поля, а не новое время на дубле. Retention
   задаётся явно целыми секундами и не превышает72часов. UUID рабочего контекста
   приводятся к каноническому регистру; opaque provider IDs не изменяются.
6. Сформировать точные JCS-байты NormalizedSignal. message_digest — SHA256 RFC8785
   полного сообщения без message_digest, с закреплённой библиотекой jcs v1.0.2.
   Сначала contentstore выполняет file fsync → rename → directory fsync; проверить
   чтение, digest и ещё действующий срок. Сырой webhook не сохраняется.
7. Только после этого начать новую короткую SQL-транзакцию, повторно проверить
   подключение с FOR SHARE, вставить signals и outbox. Применяются оба существующих
   quota-триггера/лимита:1000сигналов И16MiB/workspace. Откат убирает обе записи и
   увеличение квоты. SQL получает только разрешённые minimal identity, ref/hash/size
   и времена. Транзакционные/statement/lock timeout —2секунды.
8. После commit ещё раз проверить доступность сохранённых байтов и срок. Только
   затем вернуть локальный приём. Ошибка commit или потеря подтверждения означает
   ErrUncertain, без результата. Файл при таком исходе вслепую не удаляется: SQL
   мог уже зафиксироваться. Повтор/новый пул и файловый дескриптор находят одну запись.

Короткие ошибки ограничены безопасными кодами, без исходного сообщения SQL, payload,
секретов или контактов. В методе нет обращения к Stripe, Processing или сети иных
сервисов. PostgreSQL-соединение само по себе не является действительной authority
IAM: она остаётся явно проверяемым входом будущего рабочего контура.

## Восстановление и очистка

Ошибка до SQL оставляет не более файлового orphan. Ошибка после signals до outbox
или до commit откатывает обе записи/квоту. Потеря ответа после реального commit
не объявляется rollback и не разрешает второе исходящее сообщение.

Cleanup получает ту же блокировку, читает полный scoped список всех outbox refs
этой рабочей области, заканчивает SQL-транзакцию и вызывает существующий Purge.
Даже истёкшие/ACKED references защищены: удаление принятого SQL ref принадлежит
будущему owner retention flow. Приём и очистка используют отдельный root на workspace;
другие внешние publisher и ручная правка файлов не входят в договор адаптера.
Недоступный сохранённый файл не восстанавливается из произвольного повторного payload
и не превращается в новый приём; нужен честный незавершённый исход/разбор владельца.

## Что проверяется настоящим запуском

Go1.27.2, pgx5.11.0/JCS1.0.2, отдельная PostgreSQL18.7 Alpine по согласованному digest,
временные каталоги и только синтетические события. Параметры fsync,
full_page_writes и synchronous_commit проверяются как on. Метод использует
hp_intake_app NOSUPERUSER/NOBYPASSRLS и scoped RLS; мигратор создаёт схему/fixtures.
Read-only наблюдатель в тесте получает pg_read_all_stats только для проверки
отсутствия транзакции во время fsync. Метод не получает этих прав.

Проверены три event_type из схемы без решения о платеже, точные byte/digest readback,
последовательные и12конкурентных повторов через разные экземпляры, разные подключения
и workspace, RLS и сброс scope/lease после отката, отзыв между file и commit,
оба quota-предела при конкуренции, TTL/EXPIRED/missing content, сохранение orphan и
его очистка без удаления принятого файла, гонка cleanup с ещё не внесённым в SQL
файлом, новый pool/root handle после пересоздания метода. Byte-quota boundary
использует разрешённый синтетический seed счётчика, не реалистичную оценку нагрузки.

Сбои после signals/перед commit/после commit вводятся явно. Отдельный loopback-only
прокси действительно отбрасывает PostgreSQL CommandComplete для commit после
фиксации сервером. Проверено, что метод получает неопределённый ответ, а другой
пул видит ровно один приём и outbox; повтор не удваивает сообщение. Это реальный
локальный транспортный отказ на синтетическом соединении, не production outage.
Все прежние тесты подписи, нормализации, JCS, contentstore и377 SQL-проверок также
выполняются. Протокол: commands.json и unit/integration/schema/vet/build/modules logs.

Запуск из корня: `python3 services/intake/tools/check_receipt.py --go /path/to/go1.27.2/bin/go`.
Скрипт принимает только новый принадлежащий ему контейнер, не внешний DSN;
публикует порт только на127.0.0.1 и удаляет свой контейнер. Точный проверенный SHA,
исходные hashes, версии, команды и exit codes сохраняются автоматически.
CI pr12-intake запускает те же проверки текущего кода и сохраняет артефакт, без
возобновления исторических процедур. Исправления тестовой подготовки (одиночные
SQL-команды и окончательная готовность контейнера) не выдаются за первоначальный PASS.

## Ограничения и следующий шаг

Проверен локальный надёжный приём, не публичный webhook или доставленное сообщение.
Нет сетевого отправщика, реального Processing, установки по HTTP-маршруту,
подключённого IAM/runtime, чтения Stripe, активации или ClickUp. Tmpfs и локальные
fsync не квалифицируют рабочий диск, питание, flush, резервное восстановление или
Stripe→ClickUp E2E. Не проводилась отдельная security qualification PostgreSQL/CVE;
использован согласованный исправленный18.7, другие версии не подменялись.

Один следующий шаг — отдельный сетевой отправщик существующего outbox с сохранением
тех же bytes/message ID/digest и проверенным приёмом Processing. Новый протокол
доставки/HTTP в этой задаче не вводится. Независимый Reviewer и человеческая приёмка
пока не выполнены; серверная регистрация и READY оформляются отдельно.

Основания: закреплённый SystemDesign manifest0ff88d118e39a5dfaa34540c0d621649c34655a7,
SYSTEM_DESIGN_MVP_RU b2461564e4355ea5a72a55a30a635655397c463b (A-003/004/005/014/017/025/026),
точные OAS/PERSISTENCE/stack-mvp fedbe40bb597e25f66aeb1172af3ff7459c81b40,
и поправка PostgreSQL d9eb399d9cc0528f1beae6153851ab5020741ea5. Полный реестр и
применимые неизменяемые источники прочитаны в этой рабочей сессии. Bootstrap13668
