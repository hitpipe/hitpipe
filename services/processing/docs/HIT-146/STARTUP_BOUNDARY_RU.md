# Что требуется для снятия блокировки HIT-146

Основание — действующие HP-MVP-A-011–013 и принятый HTTPS/mTLS протокол. Открытие требует актуального снимка для точного экземпляра. ACK засчитывается от ожидаемого runtime после завершения защищённых секций старта. Пропажа прежнего экземпляра не доказывает его изоляцию. [Архитектура](https://github.com/hitpipe/project-os/blob/b2461564e4355ea5a72a55a30a635655397c463b/contracts/hitpipe/mvp-2026-10-31/SYSTEM_DESIGN_MVP_RU.md#L43-L47).

1. **Допуск новой загрузки.** Processing сам генерирует `boot_id`. Его `iamClient` передаёт этот ID и отпечаток исходящего клиентского сертификата. IAM связывает проверенный mTLS principal с заранее утверждённой полной записью и сравнивает её с запросом. Без поставленного извне авторитетного подтверждения exact boot самостоятельный перезапуск закономерно даёт 403. Смена boot требует действительного установленного барьера изоляции старого экземпляра там, где этого требует принятый IAM. [Генерация Processing](https://github.com/hitpipe/hitpipe/blob/b2e823012854575146595b01a6f56d5ac677fc44/services/processing/internal/runtime/runtime.go#L125-L133) · [Register IAM](https://github.com/hitpipe/hitpipe/blob/d13f723511b61cb3068bfdf63d40bd7100fa1e89/services/iam/internal/adapters/composition/privateiam/server.go#L127-L147).
2. **Переход удалённого runtime в OPEN.** Хранилище IAM применяет `OpenLocal` только для IAM. При сетевом `Register` результат для удалённого runtime остаётся `SYNCING`. `Authorize` отдельно требует `OPEN` для того же удалённого runtime. Даже заранее известный exact boot не решает второй разрыв. [Хранилище IAM](https://github.com/hitpipe/hitpipe/blob/d13f723511b61cb3068bfdf63d40bd7100fa1e89/services/iam/internal/adapters/postgres/runtimeaccess/store.go#L105-L119) · [Состояние снимка](https://github.com/hitpipe/hitpipe/blob/d13f723511b61cb3068bfdf63d40bd7100fa1e89/services/iam/internal/adapters/postgres/runtimeaccess/store.go#L183-L207) · [Authorize](https://github.com/hitpipe/hitpipe/blob/d13f723511b61cb3068bfdf63d40bd7100fa1e89/services/iam/internal/adapters/composition/privateiam/server.go#L217-L235).
3. **Привязка control TLS.** В принятой конфигурации Processing раздельные клиентский и серверный сертификаты. Координатор сверяет сертификат сервера барьера с отпечатком, взятым из зарегистрированной записи участника; в данном стенде зарегистрирован отпечаток исходящего клиента. Оба действительных отпечатка наблюдались и различались. Нужна согласованная доверенная привязка control-слушателя к тому же участнику. [Регистрация Processing](https://github.com/hitpipe/hitpipe/blob/b2e823012854575146595b01a6f56d5ac677fc44/services/processing/internal/runtime/iam.go#L53-L57) · [Сетевой клиент барьера IAM](https://github.com/hitpipe/hitpipe/blob/d13f723511b61cb3068bfdf63d40bd7100fa1e89/services/iam/internal/adapters/http/revocation/client.go#L90-L116).

**Вопрос для Lead и владельца IAM.** Указать принятый механизм подготовки и подтверждения точной загрузки удалённого Processing, перехода этого экземпляра в `OPEN` после применения актуального снимка и сопоставления исходящего и control TLS экземпляров. Также нужен согласованный способ включить реального IAM-участника в полную доставку и подтверждение барьера тестового контура. Если такой механизм уже принят, закрепить его реализации и точные SHA. Если отсутствует, согласовать узкое изменение на границе IAM/Processing до повторения положительной квалификации.

После решения повторить полезный запрос до отзыва, исходящий запрос с удержанным ответом, настоящий ACK полного списка и отсутствие нового old-epoch start. Таймаут оставить отдельным отрицательным сценарием. Сопоставить времена с пределом 5 секунд на каждом точном наборе сборок.
