1. Источник метки заказа

order_label = accepted_configs.canonical_config.service_label именно принятой конфигурации config_id дела, с проверкой workspace/operation/config и digest. Это каталожное название услуги; уникальная идентичность дела находится в case_id. Существующие ограничения 1–120 символов и отсутствие управляющих символов сохраняются. Невалидный/отсутствующий источник → 503 READ_UNAVAILABLE, без Session ID, case ID, revision, пустого значения, усечения или другой выбранной конфигурации. Истечение контекста не истекает принятую конфигурацию.

2. Подсказка следующего шага

next_action — понятное русское объяснение, а не код команды и не разрешение. Базовый текст сохранённого состояния:



RECEIVED: Дело получено, ожидается проверка данных.



WAITING_DATA: Ожидаются необходимые данные.



WORKING: Дело находится в обработке.



UNKNOWN: Результат внешнего действия не установлен.



ATTENTION: Есть препятствие, требующее разбора.



CONFIRMED: Результат подтверждён последней сохранённой проверкой.



EXCLUDED: Дело исключено из обработки.



CLOSED_WITHOUT_CONFIRMATION: Дело закрыто без подтверждения результата.



К нему добавляется первый подходящий следующий шаг по следующему порядку:



Реально подключён RECHECK, известна та же task identity, есть свежие полномочия именно на команду и выполнены её проверки — Доступна повторная проверка известной задачи ClickUp.



state=UNKNOWN, outcome=POSSIBLE_EFFECT либо UNESTABLISHED с сохранённым признаком возможной отправки — Нужно установить внешний результат. Повторное создание задачи запрещено.



outcome=RESULT_MISMATCH — Нужно разобрать несоответствие результата. Повторное создание задачи недоступно.



Терминальное сохранённое состояние CONFIRMED, EXCLUDED или CLOSED_WITHOUT_CONFIRMATION — Дополнительных действий с делом в этой версии нет.



Для незавершённого дела обязательный контекст достоверно истёк/удалён либо неполон — Нужны актуальные обязательные данные; новая отправка удержана.



Сохранённая распознанная причина указывает на препятствие доступа к прежней внешней identity — Владельцу нужно восстановить доступ к прежнему подключению.



state=WAITING_DATA без более приоритетной причины — Ожидаются проверенные данные. Ручное добавление данных в этой версии недоступно.



state=RECEIVED либо WORKING без более приоритетной причины — Дождитесь результата обработки.



Остальные допустимые сохранённые состояния — Требуется разбор сохранённой причины препятствия.



При UNKNOWN/POSSIBLE_EFFECT либо сохранённой границе возможной отправки запрет нового create остаётся видимым даже при доступном RECHECK. TARGET_ID_KNOWN сам по себе не подтверждает результат; RESULT_VERIFIED обозначает последнюю сохранённую проверку. Причина берётся из последней safety_history, объясняется коротким каталогом реальных producer codes. Неизвестный код явно остаётся нерасшифрованной сохранённой причиной. Штатное expiry обозначает неполноту и не меняет состояние/знание. Итоговая строка до 512 символов, без сырых ответов провайдера, секретов и произвольной диагностики.

available_actions — пересечение сохранённых в MVP, фактически подключённых команд, свежих полномочий именно на команду и выполненных её проверок. Единственный кандидат — RECHECK известной task identity. До подключения реальной команды и её проверок возвращать []; право чтения дела не разрешает команду. Установленный отказ в праве, неподтверждённая доступность и отсутствие функции в этой версии различаются пояснением. Не требовать ACTIVE для всех ручных проверок: разрешённые проверки PAUSED сохраняются; чтение закрытого/исключённого дела его не переоткрывает. Реализация recovery handler не входит в HIT-95.

3. Начальная история и истечение срока

Исправляет Тимофей Патрушев в HIT-95. Разрешено узкое исключение из прежнего запрета менять producer: первая запись SIGNAL_ADMITTED через существующие HISTORY envelope/content storage HIT-79. Сохранить одно действительное время и действующий expiry не позднее 90 суток, без продления дублями. file fsync → atomic rename → directory fsync до SQL commit; inbox/case_identity/safety_history/history_content фиксируются в одной scoped транзакции с прежними атомарностью, RLS, идемпотентностью и durable ACK. GET остаются без бизнес-записей.

После достоверного expiry возвращать минимальную safety_history + сохранённую expiry metadata без чтения уже удалённого body. episode_id=null означает, что сведения об эпизоде не представлены после истечения подробностей, а не что эпизода никогда не было. at/reason/old/new state/evidence_ref сохраняются. Минимальная expiry metadata остаётся при удалении body. Отсутствующая/повреждённая metadata либо отсутствующее/повреждённое неистёкшее body → 503. Старые записи без достоверного срока не дополнять выдуманным at+90days.

Границы и проверка

SQL/OAS не меняются; новые команды, живые провайдеры и рабочие данные не затрагиваются. Done HIT-78/HIT-79 остаются историей. Проверить непустые listCases/getCase, настоящий admission → getCaseHistory 200 без ручной подстановки history metadata, nullable-поля, отрицательные случаи, границу expiry, повторные чтения/purge/restart, RLS/mTLS, PostgreSQL 18.7, race/vet и CI.
