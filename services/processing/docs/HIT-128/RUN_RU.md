# Воспроизведение восстановления Processing

Процедура предназначена для локальной проверки HIT-128. Она сама создаёт исходный и целевой PostgreSQL 18.7 с разными системными идентификаторами, WAL и каталогами данных. Оба кластера находятся внутри одноразового Docker-контейнера с сетью `none`. Заранее подготовленная БД, внешний DSN и рабочий том данных не используются.

## Подготовка и запуск

Из корня чистой копии проверенного коммита нужны Go 1.27.2, Python 3 и локальный Docker с Unix-сокетом. Закреплённый образ можно загрузить заранее.

```sh
docker pull docker.io/library/postgres:18.7-bookworm@sha256:ece55f7868da684e400f82f1030a050718adbdd65c23aa500c486f6e2950dc0f
PYTHONDONTWRITEBYTECODE=1 python3 services/processing/scripts/recovery/verify_recovery.py \
  --go /absolute/path/to/go1.27.2/bin/go \
  --output /absolute/path/to/new-evidence-directory
```

Сценарий проверяет SHA принятой миграции и включает `fsync`, `full_page_writes` и `synchronous_commit`. Исходный кластер использует закрытый Unix-сокет. Во втором кластере PostgreSQL дополнительно слушает только loopback. Клиент проверяет сертификат и имя сервера в режиме `verify-full`. Processing, BFF, OPS, IAM, Intake и Delivery используют отдельные тестовые mTLS-идентичности. Временные ключи и файлы конфигурации удаляются со стендом.

## Что переносится

Остановленный исходный Processing оставляет проверяемое состояние. Тестовый перенос использует один read-only снимок SQL в явной области RLS и одну транзакцию в пустой области нового кластера. Обе операции используют `hp_processing_app`; контрольное обслуживание выполняется от `hp_processing_purge`. Отдельные роли настройки поднимают новую базу и применяют принятую неизменную миграцию.

| Данные | Что сохраняется |
| --- | --- |
| `operations`, `accepted_configs` | Идентичность, состояние, граница активации, закреплённая конфигурация и её digest |
| `case_identity`, `episodes` | Идентичность дела и внешнего эффекта, необратимый fence, знание об исходе и исходный бюджет попыток |
| `user_commands`, `inbox`, `safety_history` | Область, идентификаторы, исходы, хеши и краткие причины |
| `case_content`, `history_content` | Только непрозрачные ссылки, хеши, размеры и исходные сроки |
| `outbox` | Идентичность сообщения, исходные сроки, счётчик попыток и ссылки. Незавершённое переводится в `HELD` с очищенными claim/lease |

Строки передаются в памяти. Файлы содержимого читаются с прежнего service-owned каталога. Сценарий не создаёт физический snapshot, архив WAL или копию каталога. Черновики, уведомления и вычисляемый индекс рабочих заданий в перенос не входят. Тот же снимок в непустую область повторно не применяется.

## Проверки и границы

Стенд проверяет сохранение существующего дела, команды, inbox и внешней идентичности после прерванной доставки. Перед проверкой бизнес-доступа нужен корректный свежий снимок IAM для текущей загрузки и поколения. Снимок с установленным отзывом доступа удерживает отозванную область даже при ответе с более высоким epoch. Ни остаток прежней аренды, ни сам перенос SQL не служат основанием для ACK, подтверждения результата или повторного создания.

Проверяются `SIGKILL` между сохранением файла и SQL commit, отсутствующее и повреждённое содержимое, истёкшая запись до и после очистки. Сохраняется исходная метаинформация истории. Протокол содержит команды, коды, SHA, оригинальные stdout/stderr и хеши. Локальная длительность относится к этому тестовому сценарию. Она не измеряет эксплуатационный RTO.

Для рабочего восстановления требуются актуальные данные о поколении, удалениях и отзывах, подтверждение минимального знания о возможном эффекте и проверенная идентичность провайдеров. Неподтверждённые области должны оставаться закрытыми. Автоматическая загрузка рабочего архива, новый формат резервных копий и отдельный протокол удаления в HIT-128 не вводятся.
