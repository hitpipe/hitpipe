# HIT-113. Повторная проверка известной задачи ClickUp

Codex по делегации Тимофея Патрушева / Tim1hik. [Задача и контракт](https://hitpipe.atlassian.net/browse/HIT-113) · [PR №76](https://github.com/hitpipe/hitpipe/pull/76).

`recoverCase` принимает только `RECHECK`. Сервер проверяет BFF mTLS, сессию, CSRF, `CASE_RECOVER` для дела и `CONNECTOR_READ` для текущего подключения. PostgreSQL с RLS проверяет владельца, ревизию, закреплённую конфигурацию, прежнюю lineage и эпизод. Native ID берётся из сохранённого дела с установленным fence и связью с первоначальным `DeliveryIntent`. Если клиент прислал ID, он проверяется на точное совпадение.

Бизнес-ответ 202 содержит `CaseDetail` с сохранённым знанием. В одну транзакцию входят запись `user_commands`, исходящий `DELIVERY_QUERY` и история `RECHECK_ACCEPTED`. Команда с прежними `request_id`, телом, владельцем и делом восстанавливает уже сохранённое принятие и возвращает текущий вид дела. Тот же ID с другим телом получает 409. Причина хранится в истекающем файле истории Processing. SQL содержит ссылки, идентификаторы и хеши.

Фоновая отправка использует существующие аренды, mTLS и повтор HIT-98. Она отправляет только принятую структуру `DeliveryQuery` на `/internal/v1/delivery-query`. Аренда длится 10 с. На одну попытку отводится до 1,5 с. Повтор ограничен тремя попытками и исходным сроком чтения до 30 с, сокращённым сроком доказательства lineage. Все повторы сохраняют байты и Request ID. Перед фактическим началом I/O заново проверяются права, эпоха, аренда и ревизия. SQL освобождает блокировки до сетевого вызова.

Точный ответ `TaskObservation` проходит существующий HIT-99. Ответ с другой областью, lineage, эпизодом, native ID или временем вне окна удерживается. HIT-99 разрешает конкуренцию наблюдений по собственным правилам и сохраняет установленную identity. В сценарии неполного повторного чтения сохранённое знание `RESULT_VERIFIED` осталось в деле, текущее состояние стало `UNKNOWN`, ссылка скрылась. `available_actions` в деталях показывает `RECHECK` только после проверки действующего права и сохранённой identity. Список дел сообщает, когда доступность для отдельного дела ещё требуется проверить.

| Критерий | Фактическая проверка |
| --- | --- |
| 1. Версии и переиспользование | База `3b542e8` содержит проверенные HIT-95/98/99/111/112. Открытые PR указаны отдельно от `main`. Сверены точные схемы команды, запроса и наблюдения. |
| 2. Приём команды | На реальном Processing проверены BFF mTLS, отсутствующая сессия, неверный CSRF, отказ `CASE_RECOVER`, каждое отложенное действие enum, чужое дело, устаревшая ревизия и конфликт заголовка. |
| 3. Известная identity | Отказ при отсутствии известного ID, другой native ID и неподтверждённая lineage. На отправку ушли только сохранённые workspace, case, lineage и native IDs. |
| 4. Атомарность | Два конкурентных приёма дают одну команду, историю и запись outbox. Реальный SQL rollback оставляет ноль записей. Повтор после потерянного ответа успешного commit и после SIGKILL не создаёт вторую проверку. |
| 5. Типизированная отправка | Управляемый mTLS Delivery проверял точный `DeliveryQuery`, идентичность байтов повторов, epoch и deadline. Два конкурентных захвата дают одного владельца аренды. Проверены истечение, отмена и барьер отзыва после ClientHello. В сценарии RECHECK к каналу Create обращений не было. |
| 6. ACK и исход | 202 оставляет `UNKNOWN` с `TARGET_ID_KNOWN` и пустой ссылкой. После проверенного `TaskObservation` прежний HIT-99 показал `CONFIRMED` в готовом чтении. Fence и task identity сохранились. |
| 7. Ошибки и конкуренция | Неподходящие identity/lineage, поздний и неполный ответы, timeout и последовательность 429/503. Старый ответ проиграл более новому входящему наблюдению. История и детали показали фактический результат без фиктивной ссылки. |
| 8. Исполняемая проверка | Чистый код `9165e814cb7b46e9cfae484c62ccc70f63fc1ee3` прошёл реальный PostgreSQL 18.7, Linux-процесс и TLS 1.3 mTLS. Отдельно прошли Go 1.27.2 `race`, `vet`, `build` и GitHub CI `6/6 SUCCESS`. |

Проверенный стенд использовал настоящий Processing, PostgreSQL 18.7 и файлы. IAM, Intake и Delivery были управляемыми участниками с отдельными сертификатами. Для обычного запуска по-прежнему требуются авторитетные входы HIT-111. Живое чтение ClickUp, рабочие credentials и распределённый барьер не квалифицировались. RECHECK использует только чтение известной задачи и сохраняет прежнюю историю и fence.
