## Поведение и исправление

Черновик, проверка, репетиция и явная активация продолжают использовать существующие Processing модули, SQL HIT-76, собственные durable files и журнал команд. Нет нового endpoint, таблицы, financial evaluator, внешней записи или параллельного сервера. Activation и draft handlers присоединяются до ServeTLS к существующему приватному TLS1.3/mTLS listener8443, сохраняя read/Intake/Delivery routes.

Раньше HIT-100 хешировал значимые поля DraftConfig с aliases, а HIT-95 требовал SHA256 RFC8785 JCS фактического canonical_config с разрешёнными ID. Запись draft hash в accepted_configs давала201/202, затем READ_UNAVAILABLE. Поправка разрешила недостающий серверный preview и явную связь репетиции. Историческое доказательство и весь прежний пакет сохранены в [архиве до CCR](history/pre-ccr-package-0b278e5.tar.gz), а не переписаны под новые SHA.

Теперь readiness возвращает обязательный activation_preview: ровно полный canonical_config из11 полей и его accepted_config_digest при passed=true; при passed=false — null. Корреляция passed/preview и SHA проверяются сервером поверх схемы, обе запрещённые комбинации отклоняются. Единственный чистый `drafts.CanonicalConfig` строит preview, проверяет сохранённый снимок и участвует в проверке записи. Service label должен совпасть с каталожным значением из доверенного owner proof; name/aliases/секреты/proof не попадают в preview или SQL. Все существенные owner IDs проверяются, разрешающих production defaults нет.

Preview, полный ReadinessCheck и частный BindingProof сохраняются существующим fsync→rename→directory fsync механизмом до SQL refs/ответа. Готовность не создаёт accepted_configs или ACTIVE. `config_digest` readiness и rehearsal остаётся **draft hash** без name/draft_id/revision. В RehearsalRequest обязателен выбранный readiness_check_id: сервер читает именно его, проверяет текущий draft/revision/draft digest, инициатора/workspace/epoch/expiry и достоверность preview/proof. Репетиция использует выбранный снимок и прежний чистый kernel, без owner/provider вызовов; live_requests_made=0. Private CommandNode сохраняет check ID, final digest, существенный proof и исходные examples; их точный request digest сверяется с командой. CheckedAt/ExpiresAt не подменяют identity привязки.

Активация принимает окончательный hash **публично показанного** preview. Она сверяет одну пару check/rehearsal, draft/revision, оба назначения hash, текущую сессию/CSRF/права/область/epoch и свежий owner lookup. Изменение Price/List/Assignee/account/mode/каталожного значения или epoch требует нового check, rehearsal, показа и явной команды. Aliases не разрешаются в другие ID под прежним согласием. Owner lookup вне SQL row locks; read, commit и начало ответа проходят актуальный bounded actual-start gate.

В защищённой транзакции снова читаются current draft, выбранная сохранённая проверка, сроки и связанная репетиция. Записываются **именно показанные** canonical bytes после JCS; тот же final hash получает Operation и accepted_configs.digest. SQL safe_config_valid, RLS, SINGLE, CAS/uniqueness и атомарный selected_config FK сохраняются. Owner/accepted_by/at, revision и первоначальная first_activation_at связаны с конфигурацией. DB time задаёт первую границу один раз; сохранённая граница не сдвигается. Тестируемый current private proof повторно строит тот же снимок для сравнения, а не скрыто заменяет его.

Полный ответ201 сохранён в owner files до commit. Точный request_id+JCS body digest после текущей проверки доступа возвращает исходный результат после reconnect/restart/crash, expiry readiness и будущей PAUSED; не создаёт операцию, не возобновляет её и не продлевает TTL. Другой payload конфликтует. Потеря commit ACK —503, а не ложный успех; повтор восстанавливает исходный ответ. Исторические check/rehearsal без preview/явной связи не дополняются задним числом. Отсутствующее обязательное содержимое не восстанавливается из user_commands metadata.

[Полная карта полей и ошибок](FIELD_MAP.md). Формы менялись только по принятой CCR; исходный SQL/OAS в Project OS не редактировался, клиент/чужие сервисы/финансовые правила/общий CI/locks не менялись.

## История и границы

[Индекс новых запусков](history/ccr-run-index.json) сохраняет два Docker-not-ready отказа до создания БД, раннюю версию с двумя устаревшими ожиданиями числа команд для теперь запрещённой репетиции failed-check и последующие успешные SHA. [Raw история CCR](history/ccr-development-runs.tar.gz), [полный пакет до CCR](history/pre-ccr-package-0b278e5.tar.gz). Прежнее описание противоречия остаётся историей; его нормативно устранила утверждённая поправка, а не самостоятельное новое бизнес-правило.

Сессии/authority/owner bindings/actual-start — явно управляемые зависимости stand, не живые IAM/BFF/Stripe/ClickUp и не production credentials. Это не весь MVP, нагрузочный/SLA/power-loss/deployment прогон и не реальное человеческое принятие. Тестовый caller явно отправляет выбранный hash публичного preview; frontend HIT-97 здесь не менялся. Репетиция не получает внешних портов.

Сохраняется существующая явная TTL policy, в тестах draft content1ч/check1мин (не новые продуктовые пороги); full response после истечения/очистки содержимого даёт503, SQL minimal accepted configuration сохраняется. Пауза/возобновление/архивирование не реализуются этой задачей. Точная техническая квитанция повтора не сдвигает first_activation_at, не продлевает readiness и не запускает новый эффект.

Официальный результат/evidence регистрируются по опубликованному представлению; handoff-preflight запрашивается один раз после проверки. Только свежий официальный READY позволяет объявить готовность к личному In Review. Даже при READY PR остаётся Draft по прямому поручению пользователя. Агент не меняет статус Jira, не начинает независимое ревью, не выставляет PASS/Done и не сливает PR.
