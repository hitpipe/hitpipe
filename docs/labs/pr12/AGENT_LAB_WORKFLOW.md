Версия: 2026-10-17. Режим: **MANUAL_LAB_PR12**. Владелец процесса и человеческих решений — Дмитрий Карачебан (Lead). Набор источников: четыре методички МДК01.04 ПР1/ПР2 и МДК03.02 ПР1/ПР2; исходные файлы и SHA перечислены в manifest. Срок подготовки сдачи: 19 октября 2026, Europe/Moscow; точное время определяется преподавателем, эта инструкция его не придумывает.

Это временный ручной процесс для явно порученных пользователем учебных задач. Он использует предметную спецификацию HitPipe и дисциплину Project OS, но не является официальным runtime Project OS. Не вызывайте `/start`, `/review`, `confirm-start`, FORCE, repair или service-token bridge ради этих задач. Не создавайте фиктивный bootstrap и не выставляйте `authority_ready`, `execution_authorized`, Accepted или официальный faithful-review. Прямое поручение Lead разрешает подготовку и реализацию ограниченных учебных модулей с синтетическими данными, тестами и PR; оно не означает formal Development admission, production deployment, живые внешние эффекты или человеческую приёмку контрактов.

## 1. Что должен получить агент

В мастер-промпте требуется только реальный ключ Feature конкретного участника. Из Feature и связанного manifest агент получает имя и код участника, component, repository, epic, дочерние рабочие карточки (Jira Subtasks, когда Feature и Task находятся на одном стандартном уровне), ссылки на этот workflow, исходные методички/шаблоны, context lock и единственного владельца общего кода. Не просите участника пересказывать историю проекта.

Обязательный marker Feature и каждой Task: `MANUAL_LAB_PR12`. Если marker отсутствует, не применять этот режим автоматически: это может быть обычная frozen Task Project OS. При недоступной Jira агент может подготовить локальный результат по полному versioned export задачи, но отмечает Jira state unknown и не утверждает, что перевёл/закрыл её. Для записи нужны собственные разрешённые инструменты пользователя, не общий секрет Project OS.

Не назначайте личность автоматически по доступному токену. Assignee человека и исполнитель агента — разные сведения; приглашённый участник может оставаться unassigned. Фамилия в Feature/manifest сохраняет ownership.

## 2. Контекст и безопасное начало

1. Прочитать локальный AGENTS.md и вложенные инструкции, фактически загрузить общий Project OS AGENT_MASTER_PROMPT. Затем применить явное ручное поручение из мастер-промпта и этот workflow только к помеченной области ПР1–2.
2. Прочитать Feature, все её дочерние задачи и `context-lock.json`/эквивалентный immutable manifest. Проверить реальную ветку, чистоту рабочего дерева, owner component, WORK DEST и blockers. Существующие чужие правки сохранить; создавать отдельную рабочую ветку/worktree.
3. Прочитать общий charter, нормы изменения и только применимые нормативные документы: DA/Vision для смысла; Product Contract и выбранные FR/NFR/RULE; AD, свой BP, BP007 и затронутые правила BP006. Полные общие wire/SQL использовать по pin, без переавторства локальных схем. Pin/revision с actual content сравнить с lock; изменившийся/недоступный обязательный source удерживает затронутую работу до выяснения.
4. Baseline является **Candidate/In Review**, если не предоставлена настоящая запись acceptance. Его использование как учебного design input обозначается явно. Нельзя выдавать учебный baseline/tag за принятый фазовый контракт или реализацию всего MVP.
5. Из задач выбрать первую готовую по зависимостям. Готовность — наличие перечисленных входов; наличие карточки не означает, что внешний сервис или соседний модуль уже существует. Для изолированных тестов применять объявленные in-memory/fake adapters по контракту, не ждать полного deployment соседних микросервисов.
6. Кратко записать цель, task key, base SHA, context lock, рабочую ветку и planned checks. Отдельного разрешения на каждую безопасную правку не нужно: оно уже дано Lead на ручной учебный scope.

## 3. Единый execution contract карточки

Далее «Task» означает рабочую карточку с execution contract; фактический Jira issue type может быть Subtask. Действующий adapter Project OS поддерживает logical Task поверх physical Subtask; один issue type сам по себе всё равно не запускает official runtime. Каждая Task должна содержать следующие поля в описании. Отсутствующее существенное поле не следует выдумывать; агент фиксирует конкретный blocker или предлагает узкое уточнение Lead.

| Поле | Содержание |
| --- | --- |
| MODE / OWNER | MANUAL_LAB_PR12; Feature; component; код и ФИО участника |
| OUTCOME | Один наблюдаемый результат и его пользовательский/инженерный смысл |
| SOURCE / CONTEXT | Exact source pins/revisions, номера FR/RULE/NFR/BP/T, methodic result IDs; смысл источника и его статус |
| INPUTS / DEPENDS ON | Конкретные готовые файлы, merged PR/commit либо согласованный port; отдельные human gates |
| WORK DEST | Repo, PRIMARY paths, allowed RELATED paths, конкретное место конечного результата |
| DO NOT TOUCH | Чужие сервисы; shared schema/lock/root CI без согласованного владельца; secrets; deployment |
| CONTRACT | Входы, допустимые/недопустимые значения, результат, ошибки, порядок при конфликте, side effects, ownership |
| IMPLEMENTATION / CHECKS | Bounded module, production consumer/port, позитивная/ошибочная/граничная проверка, воспроизводимая команда |
| DOD IDs | Именованные проверяемые условия; каждому — путь результата и способ установления |
| EVIDENCE | Actual commands + exit codes + UTC/МСК время + full SHA + environment/tool versions + artifacts/CI links |
| HUMAN HANDOFF | Требуемое действие человека; что агент может продолжить параллельно; условия реального закрытия |
| CONTINUATION | Будущий component/area epic; public contract; ограничения и остаток после текущего вертикального среза |

Task Contract в этом формате — ручное описание задачи, не подделка frozen Task Contract платформы. Нельзя вписывать несуществующие freeze fingerprints, wave approvals или backend readiness.

## 4. Структура исходников и module boundaries

Для Go выбираем ports-and-adapters внутри каждого собственного service module: `cmd/<service>/` — composition root; `internal/domain/` — чистые типы/правила; `internal/application/` — use cases и требуемые ими ports; `internal/adapters/inbound/` — HTTP/CLI; `internal/adapters/outbound/` — storage/HTTP/provider implementations. Допустимо более компактное именование при сохранении этих зависимостей. Не создавать пустой framework из пяти слоёв ради одного правила.

Domain не импортирует HTTP/framework/SQL/provider SDK; application зависит от domain и своих ports; adapters реализуют ports; только composition root связывает конкретные реализации. Продуктовая бизнес-логика не живёт в HTTP handlers, transport DTO или общей межсервисной библиотеке. Каждый сервис владеет своей DB; прямого cross-service SQL нет. Generated wire types не заменяют собственный domain model и не копируются изменяемыми вручную в каждый сервис. Критичный внешний port должен допускать тестовую подмену без изменения потребителя. Никаких hidden retries внешнего POST после неизвестного исхода.

Для Next.js: `app/` — routes/layout и server composition; `features/<bounded-feature>/` — model/use case/UI; `lib/server/` — server-only adapters/BFF, `lib/contracts/` — generated/checked wire. Client component не получает секреты, business authority, service-token или прямой доступ к DB. Чистая функция представления статуса не выдаёт stale/unknown за success. Python AI относится к текущему scope только если явно включён карточкой: никакого живого provider call/AI расширения ради лабораторной.

Целевая папка backend — `services/<service>/`; frontend — текущий client repo, с отдельной границей нового Next приложения, если она уже зафиксирована scaffold-карточкой. Не мигрировать весь legacy code и не переписывать корневые build files параллельно с другим владельцем. Общий scaffold, versions и корневой CI меняет только назначенный Lead owner; в своей Task агент добавляет изолированный module и точную include/path-filter инструкцию. Локальные module conventions — обратимое refinement архитектуры, а не новый фазовый ADR Catalog. Решение по модулю фиксировать отдельным engineering ADR с областью и ссылкой на архитектурный upstream.

## 5. Кодовые задачи и PR

В Feature ровно три собственные code Tasks, каждая даёт осмысленное развитие реального модуля: контракт и базовый business slice; интеграция через port/потребителя и негативные границы; расширение проверки/наблюдаемого поведения и доказательства. Точный scope задают карточки, его не заменяют этим примером. Однотипность учебных результатов не означает одинаковый код пяти участников.

Одна Task → отдельная ветка `work/<TASK-KEY>-<slug>` → отдельный PR с Task key, scope, нормативными ссылками, проверками и границами. Ветки не содержат чужую незавершённую работу. Для зависимого PR допустима явно обозначенная stacked branch с base на предшественнике, но после merge база и CI повторно проверяются. После merge подтянуть main и выполнять следующую задачу от новой базы. Не изменять history опубликованной чужой ветки; конфликт разрешать в собственной с meaningful verification.

Минимум перед handoff: build/typecheck (применимо); содержательные tests с assertions; штатный/ошибочный/граничный исход; отсутствие secrets; корректные инструкции запуска. Использовать exact tested/locked cohort архитектуры, а не случайный latest package. Если сборка обнаружила несовместимость baseline, исправить в своей границе, отразить факт; изменение shared contract/stack — Lead handoff. Не запускать весь production stack ради pure module tests.

Агент может открыть/обновить PR и оставить результат в review-ready статусе, доступном в реальной схеме Jira. Используется существующее поддерживаемое представление Epic → Feature (standard) → Subtask: adapter Project OS отображает physical Subtask в logical Task; parent links настоящие. Epic Link/Parent выбираются по реально доступным полям. Официальный runtime Project OS для этих Subtask не объявляется активным. Human Lead делает независимый review, настройки защиты, merge и разрешённое закрытие. Собственный self-review агента не считается человеческим review или другой персоной. Наличие approval без содержательной проверки не заменяет методический результат.

## 6. Учебные артефакты и доказательства

Индивидуальное дерево: `docs/labs/pr12/<student-code>/` с `requirements.md`, `module-contract.md`, `test-design.md`, `risk-register.md`, `module-map.md`, `engineering-adr.md`, `evidence/`, `reports/`, `handoff.md`. Общие документы — `docs/labs/pr12/shared/`; на них ссылаются exact revision/commit, не создают пять конкурирующих MVP. Идентификаторы local lab FR/NFR связываются с каноническими HP IDs; они уточняют проверяемый slice и не вводят второй нормативный источник продукта.

Для evidence вести индекс: `id, task, dod_id, kind, source_sha, command, environment, started_at, exit_code, actual_result, artifact_path, sha256, limitations`. Статусы: PASS — проверка реально выполнена и критерий соблюдён; FAIL — выполнена и нарушен критерий; BLOCKED — выполнить мешает конкретная зависимость; NOT RUN — ещё не выполнялась. **Явное указание пользователя: агент НЕ делает и НЕ подделывает скриншоты. Во всех отчётах остаются только текстовые места для них и исчерпывающие инструкции человеку.** Для каждого screenshot ID сохраняется: точный путь вставки в DOCX, источник/URL или вкладка, пошаговая навигация, воспроизводимая команда и cwd, какой commit/tag выбрать, какие поля/строки должны быть видны, подпись рисунка, имя целевого PNG, правила обрезки и редактирования секретов. Ни synthetic terminal image, ни сгенерированная картинка, ни чужой пример не считаются доказательством. Полный журнал действительного запуска агент сохраняет отдельно. Screenshot placeholder не означает, что сама проверка была выполнена: в results остаётся фактический PASS/FAIL/BLOCKED/NOT RUN. Не сохранять secrets, лишние PII и личные cookies в artifacts.

ПР1 требует собственных вопросов обследования и подлинного источника ответов; существующие DA/исследования можно использовать как desk research с указанием происхождения, но не выдавать за собственный разговор. Своё значимое изменение проходит task→branch→PR→CI→human independent review→merge; DoD проверяется по actual evidence. Проверка однозначности другим студентом и оппонирование другого проекта — отдельные реальные действия. Если замечаний не было, фиксируется реальный рассмотренный scope/участники/исход; искусственные замечания не придумываются.

ПР2: минимум две техники test design; reproducible fixtures из clean clone без личных доступов; фактические local tests и CI на сдаваемом SHA; coverage artifact с разбором непроверенного участка/предела; риски с матрицей методички, включая security risk и влияние на частоту проверок. Test oracle — requirement/независимый расчёт, не выход тестируемой программы.

Mutation experiment: исправная baseline зелёная; временная отдельная ветка/worktree без автоматического merge; не менее пяти компилируемых поведенческих дефектов **по одному**; для каждого сохранить diff, mutated SHA/patch digest, build result, test command/log, нарушенную норму, killed/survived. Compile failure — INVALID, не обнаруженный дефект; заменить другим. Survivor требует причину, усиление набора и повтор с сохранением обоих результатов. В финале восстановить код, проверить diff/cleanliness, повторить green tests. Summary: seeded/detected/missed, естественные найденные дефекты с реальными Task links (0 допустимо, не придумывать ошибки). Не оставлять мутации в сдаваемой ветке. Это контролируемый инженерный эксперимент, не фиктивный FAIL CI основной ветки.

## 7. Отчёты: два конечных DOCX на участника

В `reports/` сохраняются `0302-pz01-<code>.docx` и `0302-pz02-<code>.docx`, редактируемые исходники Markdown/JSON, assets и manifest evidence. Использовать переданные шаблоны, сохраняя титульный лист и общую структуру. При расхождении содержания приоритет — последняя методичка; корректировки минимальны и перечислены в `template-adjustments.md`.

ПР1: сведения/вариант/версия; цель; место участка в общем сценарии/MVP; собственные вопросы и источники ответов, факты/гипотезы; FR error NFR и критерии; подготовка данных/пять security вопросов; significant PR+DoD; cross-project opposition и решения; проверка однозначности; личный вклад/ограничения/материалы. Подготовить три места для рисунков и инструкции получения: Task+PR; CI сдаваемого SHA; реальное обсуждение замечания/оппонирование по методичке. Не подделывать отсутствующее обсуждение.

ПР2: объект и источники ожидаемых исходов; две техники; test cases и fixtures/reset; фактическая автоматизация+CI; risk registry; local/CI results; coverage analysis; **серия >=5 дефектов** вместо одного дефекта старого шаблона, таблица каждой мутации, surviving/retest и итог; восстановление; ограничения и личный вклад. Подготовить пять мест для рисунков с инструкциями получения: локальный прогон; CI; coverage; обнаруженная мутация; финальный зелёный прогон. Поле hidden suite остаётся честным: «не предоставлен/не запускался» не превращается в PASS и не должно самостоятельно блокировать локальный комплект.

Оба DOCX должны открываться без повреждений, сохранять все строки таблиц, читабельные изображения/подписи/ссылки, корректную пагинацию и оглавление. Агент проверяет извлечённый текст/число таблиц/placeholder-областей и визуально rendered PDF/страницы, если доступен реальный renderer. Если renderer отсутствует, это явное ограничение проверки, а не заявление о просмотре. Не заполнять подпись, оценку преподавателя и не угадывать группу/кафедру. Известные данные ФИО берутся из manifest; неизвестные персональные сведения остаются полями для участника и перечисляются в handoff.

Report status `PREPARED_FOR_REVIEW` возможен до человеческих gates; `CONTENT_READY_IMAGES_PENDING` — после содержательных проверок, с ожидаемыми пользователем пустыми местами для снимков; `SUBMISSION_READY` — только после всех обязательных реальных действий, человеческой вставки снимков и evidence. Пользователь намеренно оставляет вставку снимков себе; это не основание удерживать завершённую агентную часть задачи, если её DOD явно ограничен content-ready. Полная сдача Feature имеет отдельный human gate. Тег не подменяет их. После merge и проверки сдаваемой версии Lead/уполномоченный участник создаёт **непереносимые** теги `0302-pz01-<code>-v1` и `0302-pz02-<code>-v1`; доработка создаёт v2, старый тег не переставлять. Если report находится внутри коммита, не создавать бесконечный commit ради собственного SHA: `tag → commit → CI` занести во внешнюю submission record/Jira comment после тега. Никакой отчёт не утверждает, что защита уже состоялась.

## 8. Human gates и продолжение без простоя

| Действие | Кто реально выполняет | Агент до/после |
| --- | --- | --- |
| Источник потребностей/обследование | Пользователь или согласованный с преподавателем представитель | Готовит вопросы; использует только реальные ответы; desk research явно отдельно |
| Однозначность требований | Другой студент команды; для одиночного проекта назначенный преподавателем проверяющий | Готовит blind scenarios без подсказки ожидаемого исхода, сохраняет реальные ответы и исправляет расхождения |
| Cross-project opposition | Студенты другого проекта по назначенному преподавателем кольцу | Готовит пакет/вопросы, разбирает реальный чужой пакет, фиксирует настоящее обсуждение |
| Значимый review/merge/защита ветки | Lead/разрешённый human reviewer | Открывает PR, предоставляет evidence, исправляет замечания, ждёт реальный merge |
| Проверка чужого модуля (если применим МДК01.04) | Другой реальный студент | Готовит воспроизведение и регистрирует действительные замечания |
| Индивидуальная защита | Сам студент, без генеративного ИИ | Готовит краткую памятку и объяснение собственных решений, не изображает прохождение защиты |

Lead организует инфраструктуру и эти внешние контакты. Его полномочия не превращают его в другого студента/другой проект; нельзя заполнять за них свидетельство. Human pending не блокирует независимые технические задачи: продолжать готовые code/test/docs ветки, собирать evidence, выдавать единый конкретный handoff. Не закрывать зависящую DOD до настоящего результата.

При возобновлении прочитать Jira/PR current state, handoff, последние commits и evidence index. Не повторять уже прошедший mutation experiment без изменения кода/тестов или конкретной причины. Failed CI исправляется в связанной ветке; чужое отклонённое approval не обходится. Завершить, когда три code Tasks реально готовы и приняты Lead, учебные обязательные результаты покрыты evidence, отчёты/приложения выбранного report profile открываются и соответствуют actual tagged SHA, места снимков снабжены полной инструкцией. Агентный scope может завершиться `CONTENT_READY_IMAGES_PENDING`; финальная сдача и обязательные внешние действия остаются у Lead/участника. Feature/Epic closing — Lead, а не автономный Worker.

## 9. Что отдаёт агент при остановке/завершении

`handoff.md`: последняя ветка/SHA/PR, task/DOD statuses, что действительно выполнено, exact команды, где artifacts/reports, открытые замечания, human gates с одним следующим действием, следующие готовые Task keys, список не реализованного полного продукта. Future area epic не требует переписать код: сохраняются component, task history, module paths/ports, accepted PRs и requirement traceability; меняется организационная принадлежность задач или добавляются ссылки по решению Lead. Текущий учебный эпик не объявляется полнотой сервиса или закрытием HP-VER-001.


## 10. Полное покрытие четырёх методичек

Не сокращать выполнение до МДК03.02 только потому, что приложены два DOCX-шаблона. В контекст входят все четыре методички. Формат сдачи зафиксирован в Feature manifest как `report_profile`: `TWO_0302_REPORTS_WITH_0104_APPENDICES` (два основных отчёта и два чётко отделённых приложения) либо `FOUR_SEPARATE_REPORTS` (четыре самостоятельных отчёта). Агент не выбирает формат заново на каждой Task. Пока профиль не уточнён, выполнять общие код/тест/evidence задачи и хранить четыре исходных report modules отдельно — это позволяет собрать любой из профилей без переписывания. Наличие приложения само по себе не доказывает, что преподаватель согласовал объединённую форму; это отражается в submission checklist.

| Методичка | Личный проверяемый результат | Обязательные human границы |
| --- | --- | --- |
| 01.04 ПР1 | Своя часть executable scaffold; конфигурация влияет на поведение и invalid config даёт ошибку; version → source; безопасные start/result diagnostics; семь позиций toolchain с фактическим/плановым статусом; схема source→runtime; один сценарий dev и delivery с реальными командами/составом binary/package; delivery launch вне исходников; содержательная CI; clean-room инструкция | Другой студент запускает часть, которой не был автором; собственный запуск не заменяет эту проверку |
| 01.04 ПР2 | Свой модуль с логикой и production consumer; контракт поведения/ошибок/владения/side effects; GoDoc/TSDoc; один неизменяемый consumer и две внедряемые реализации; normal/boundary/error для обеих; карта с направлением source dependency, легендой и правдивыми statuses; >=2 направления системной сложности с объектом/вопросом/готовностью; существующий candidate module и свой ADR с альтернативами/ценой/проверкой | Реальная проверка чужого модуля и действительный отзыв на собственный; автор/его агент не имитируют другого студента |
| 03.02 ПР1 | Charter+вклад; свои вопросы/ответы и отличие facts/hypotheses; положение в MVP; FR/error/NFR+AC; fixtures+security; своё significant change по PR/CI/DoD; actual remarks and resolutions | Реальное обследование; другой студент проверяет однозначность; другой проект выполняет opposition; человеческий review/merge |
| 03.02 ПР2 | Свой существенный модуль; test oracles; >=2 техники; clean fixtures; реальные local/CI tests; coverage analysis; >=5 compiled behavioural mutations отдельно, survivors/retest и restoration; risk matrix с security и частотой | Независимые проверки и защита; непредоставленный hidden suite честно остаётся неизвестным |

Свой вклад в scaffold и общий инженерный ADR не заменяют собственный business module/ADR. Fake dependency не должна возвращать success всегда: обе реализации соблюдают один наблюдаемый контракт в declared supported domain; различия и ограничения фиксируются. Не подменять внешнюю систему production fake adapter-ом после лабораторной: сохраняется port и отдельный будущий реальный adapter scope.

Теги для 01.04: `0104-pz01-<code>-v1`, `0104-pz02-<code>-v1`; для 03.02 — соответствующие `0302-*`. Все четыре могут указывать на один реальный финальный commit, если на нём содержится полный проверенный результат, но названия остаются разными и неизменяемыми. Не использовать generic tag `PR1` вместо предусмотренных сдач.

Для 01.04 ПР1 подготовить ровно семь предусмотренных мест: (1) собственный фрагмент кода; (2) сборка dev/delivery с существенными настройками; (3) запуск delivery вне исходников; (4) штатный запуск с командой/версией/результатом/exit; (5) invalid configuration с ошибкой/exit; (6) независимое воспроизведение другим студентом с окружением/SHA/командами/результатом; (7) локальный запуск CI-проверки при нарушенном условии, который завершается ошибкой. Последнее — обязательный настоящий sensitivity check автоматизации, не декоративный статус CI; агент проводит опыт и сохраняет журнал, человек затем делает снимок по инструкции. Ссылка на реальный успешный CI сдаваемой версии сохраняется отдельно. Для 01.04 ПР2 — шесть мест: public contract+implementation; GoDoc/TSDoc; consumer+две реализации; module map; три типа проверок обеих реализаций; настоящая взаимная проверка. Список берётся из actual methodic/requirements matrix, а не только из этого сокращения.
