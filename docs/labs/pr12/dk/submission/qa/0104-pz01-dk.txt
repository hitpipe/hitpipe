ВВЕДЕНИЕ

     Цель работы — подготовить исполняемый компонент проекта HitPipe и
проследить весь путь от исходного кода до проверенного запуска. На
индивидуальном участке реализована проверка пригодности существующей
прикладной сессии. Одна и та же логика используется прикладным
потребителем и диагностической командой.
     Задачи работы: выбрать и описать инструменты, собрать компонент в
двух режимах, исследовать исполняемый файл, проверить конфигурацию и
диагностику, воспроизвести запуск другого компонента и показать, что
автоматическая проверка действительно обнаруживает нарушенное правило.

2 ЦЕЛЬ, ПРОЕКТ И СОБСТВЕННАЯ ЧАСТЬ

     HitPipe сопровождает бизнес-операцию от входного события до
установленного результата либо понятного ожидания или исключения. Для
работы   оператора   требуется    действующая        прикладная      сессия.    IAM
определяет, известна ли сессия, не отозвана ли она и не истекли ли её сроки.
При этом действующая сессия сама по себе не разрешает бизнес-действие:
проверка роли и текущих полномочий выполняется отдельно.
     Индивидуальный       результат       находится      в      services/iam.   Это
самостоятельный Go-модуль с чистой предметной логикой, прикладным
сценарием, подменяемыми зависимостями и диагностическим исполняемым
файлом. Команда работает только с синтетическими входными данными и не
обращается к БД, платёжным сервисам или языковой модели.

3.2 Путь исполнения и состав артефакта

     Путь исполнения имеет следующий вид: исходники Go и go.mod →
проверка типов → компиляция пакетов → линковка со средой выполнения Go
→ ELF-файл → запуск процессом ОС → main и сборка зависимостей → чтение
входных данных → Lookup → Clock → Evaluate → безопасный результат и
код завершения.
     Python, Git и инструменты сборки нужны для подготовки и проверки, но
не для исполнения готового бинарника. JSON-файл передаётся отдельно.
Проверки file, go version -m и readelf показали статический ELF64 x86-64,
наличие .debug_info и отсутствие динамической секции у исследованных
сборок. Значение CGO_ENABLED=1 в метаданных само по себе не означает
динамическую линковку именно этого файла.

3.4 Конфигурация, остановка и повторный запуск

     Конфигурация задаёт путь к синтетическому входу, формат ответа и
выбор адаптеров. Корректный запрещающий результат — например,
истёкший срок — является обработанным бизнес-исходом и имеет код
завершения 0. Неверный JSON или неизвестный формат дают код 2.
Недоступная зависимость даёт код 3.
     Команда выполняет один сценарий и завершается. Она не хранит
состояние между запусками и не меняет исходный JSON. Повторный запуск с
теми же значениями и фиксированным временем даёт тот же результат. После
ошибочного файла восстановление состоит в выборе корректного входа;
очистка внешних ресурсов не требуется.

4.3 Автоматический контроль с отрицательной демонстрацией

     Workflow pr12-iam проверяет не только компиляцию, но и выполнение
именованных    тестов,   отсутствие   запрещённых   зависимостей,   запуск
бинарника и поведение при нарушении правил. Успешный запуск
проверенной версии — run 39177171258.
     Для отрицательной демонстрации в отдельном временном рабочем
дереве изменено сравнение срока бездействия: вместо now>=deadline
использовано now>deadline. Мутант M01 компилируется с кодом 0, но та же
команда проверки завершается с кодом 1: тест равенства срока обнаруживает
ошибку. После восстановления исходного файла проверка вновь завершается


                                      16
с кодом 0. Таким образом, успешная компиляция не маскирует нарушение
