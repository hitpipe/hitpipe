# Shared Definitions & Rules — HitPipe

**ID документа:** HP-DOC-SHARED-001. **Рабочее состояние:** In Review. **Ответственный за содержание и интеграцию:** Codex, делегированный Product Owner. Это кандидатный нормативный источник Product Definition, не запись формальной приёмки. Точные revisions разрешаются итоговым source manifest.

## 1. Область общих определений и правил

Определения и RULE этого документа общие для HP-CAP-001–004. Здесь находятся идентичность дела, бизнес-состояния, границы первой операции, подтверждение результата, полномочия и непрерывность. Сценарии и FR находятся в Capability Modules; независимые обязательства качества — HP-DOC-NFR-001; POL/PRIN — HP-DOC-VISION-001. Включение RULE по ссылке не включает автоматически capability или всю будущую версию.

## 3. Общие продуктовые RULE

### HP-RULE-001

**Устойчивая идентичность и связь. Нормативная роль:** общий инвариант.

**Применимость:** сигналы, дела, попытки и изменения HP-PACK-001.

**Правило:** один исходный заказ определяется сочетанием подтверждённого Stripe account, test/live-контекста и Checkout Session ID. В workspace для одного такого заказа допускается одно дело выбранной операции. Версия правила, event ID, ручной повтор и смена оператора не создают новую идентичность. Ссылка на назначение сохраняет связь с делом. Повторное событие добавляет наблюдение к существующему делу и не разрешает дополнительное создание задачи.

**Исключения:** разные Session не сливаются по email, сумме или похожему названию. Между workspace данные не раскрываются; организационный допуск одного источника задаётся HP-RULE-011. Срок сохранения минимального признака обработки определяется HP-NFR-009. Основание HP-POL-002/005; это предел поддерживаемой идентичности, не exactly-once внешнего мира.

### HP-RULE-002

**Каноническая модель состояний дела. Нормативная роль:** общее продуктовое правило.

**Применимость:** каждое дело. Каноническое состояние одно; журнал хранит предшествующие факты. Все состояния доступны уполномоченным участникам с объяснением и ответственным HP-RULE-010.

| Состояние | Однозначный смысл | Разрешённые следующие состояния и условия |
| --- | --- | --- |
| Получено | Подлинный кандидат оплаченного заказа принят в сопровождение определённой операции; полная проверка условий действия ещё не завершена, внешнее действие не начато | Ожидает данных при нехватке согласованного контекста; Выполняется при достаточных данных и разрешённом действии; Требует внимания при известном препятствии/недоступности обязательных фактов; Исключено только если проверка установила неприменимость до внешнего эффекта |
| Ожидает данных | Не хватает перечисленных обязательных данных; запись назначения не разрешена | Выполняется после допустимого дополнения и проверки; Требует внимания при недоступном подключении/превышенном ожидании по HP-NFR-003; Исключено при установленной неприменимости до любого возможного внешнего эффекта; Закрыто без подтверждения по HP-RULE-013 |
| Выполняется | Разрешённая обработка/подтверждение продолжается в пределах времени HP-NFR-002/003 | Подтверждено при HP-RULE-007; Исход неизвестен при возможном внешнем эффекте без достаточного знания; Требует внимания при установленном препятствии без неоднозначного внешнего эффекта; Исключено только при установленной неприменимости до любого возможного внешнего эффекта |
| Исход неизвестен | Внешняя запись могла состояться, подтверждения недостаточно | Подтверждено после достаточного чтения связанного назначения; Требует внимания после достоверного установления отсутствия эффекта либо существующего, но не соответствующего условиям назначения; Закрыто без подтверждения по HP-RULE-013. Установленное существование несоответствующей задачи сохраняется и не разрешает новое создание; отсутствие результата поиска не является самостоятельным условием перехода |
| Требует внимания | Известно конкретное препятствие/несоответствие; оно не скрывает неизвестный эффект | Ожидает данных при необходимом дополнении; Выполняется после устранения и допустимого основания продолжения; Подтверждено после проверки исправленного/связанного назначения; Закрыто без подтверждения по HP-RULE-013. Исключено только при установленной неприменимости и достоверном отсутствии любого прежнего возможного эффекта. Если обнаружена неоднозначность эффекта — Исход неизвестен |
| Подтверждено | Целевой handoff установлен по HP-RULE-007 на указанный момент | Требует внимания либо Исход неизвестен при новом подтверждённом наблюдении о несоответствии/неизвестности; прежний факт подтверждения остаётся в истории. Само течение времени не является проверкой текущего назначения |
| Исключено | Установлена неприменимость поддерживаемого правила до внешнего эффекта, с конкретной причиной | Получено только по явному пересмотру владельцем, если новые подтверждённые факты устранили причину в пределах исходной конфигурации и временной границы и прежний внешний эффект не мог возникнуть. Иначе исключение сохраняется с объяснением отказа. Пересмотр сохраняет identity и историю; не создаёт новое дело и не разрешает действие без новой проверки всех применимых условий |
| Закрыто без подтверждения | Владелец явно завершил работу над делом без утверждения целевого результата | Только явное возобновление владельцем в прежнюю известную область: Ожидает данных, Требует внимания либо Исход неизвестен. Предыдущая неизвестность, попытки и ограничение повторного создания сохраняются |

**Инварианты:** отсутствие подтверждения не кодируется как успех; закрытие не доказывает отсутствие эффекта; переходы не стирают историю. Истечение срока само по себе не разрешает новое внешнее действие. Ошибочный сигнал без достаточного основания оплаты может оставаться записью входящего сигнала, не создавая дело; это не запрещает последующий оплаченный сигнал по HP-RULE-006.

**Исключения и зависимости:** иных переходов нет в выбранных профилях; операции восстановления ограничены HP-RULE-005/008/012/013 и HP-POL-001–005. Технические внутренние состояния этим документом не определяются.

### HP-RULE-003

**Жизненный цикл операции. Нормативная роль:** общее правило.

**Применимость:** подготовка и управление операцией, отдельно от состояния дел.

| Состояние | Условие и допустимое изменение |
| --- | --- |
| Черновик | Конфигурация ещё не принята. Может редактироваться; live-действия не разрешены |
| Подготовлена | Есть полная проверенная конфигурация и репетиция; ожидается явная активация владельцем. Изменение значимого значения возвращает к проверке |
| Активна | Новые допустимые заказы принимаются; существующие дела продолжаются по своей версии |
| Завершается приостановка | Приём новых дел остановлен; ранее принятые дела могут закончить уже разрешённую обработку. Новые рискованные действия и изменения правил не получают разрешения от самой приостановки |
| Приостановлена | Фоновое продвижение не выполняется. Существующие дела, данные, ответственность и неизвестные исходы доступны; ручная проверка фактов и закрытие в разрешённых пределах сохраняются |
| Архивирована | Новые дела и фоновое продвижение запрещены; история доступна по retention. Архивирование допускается после приостановки и явного решения владельца о каждом незавершённом деле; архив не означает подтверждения их результата |

**Переходы:** Черновик→Подготовлена после HP-CAP-001; Подготовлена→Активна после принятия; Активна→Завершается приостановка по команде владельца; Завершается приостановка→Приостановлена после завершения уже разрешённых попыток или перевода их в явное незавершённое состояние в пределах HP-NFR-003; Приостановлена→Активна после проверки подключения и подтверждения возобновления; Приостановлена→Архивирована при указанном условии. Смена настроек приостановленной операции создаёт новую версию по HP-RULE-004, а не правит принятую. Архивирование не отменяет HP-RULE-001/013.

**Сигналы во время паузы:** допускаются в ограниченную наблюдаемую очередь приёма по HP-NFR-004, без новых внешних действий. Перед возобновлением владелец видит число/диапазон удержанных сигналов и выбирает обработку допустимых сигналов по конфигурации, активной на момент их нового допуска, либо явное исключение с причиной. Желаемая конфигурация принимается до возобновления; произвольного назначения прошлой версии отдельному новому делу нет. Уже созданные дела не перепривязываются и продолжаются по своей закреплённой версии. Ограниченная очередь не обещает восстановление всех пропущенных внешних событий; HP-NFR-004 определяет границы и видимость потерь.

**Потеря доступа:** изменяет пригодность затронутого подключения и удерживает затронутые действия по HP-POL-001 независимо от lifecycle операции. Операция не может показываться полностью исправной при таком препятствии. Работа с незатронутыми фактами сохраняется; автоматического переключения аккаунта нет.

### HP-RULE-004

**Версия и момент применимости. Нормативная роль:** общий инвариант.

**Применимость:** активация и изменение правила, обработка накопленных сигналов.

**Правило:** дело получает одну принятую конфигурацию при первом допуске исходного заказа в дело определённой операции, до последующих проверок и любого внешнего действия. Допуск кандидата в «Получено» не подтверждает его окончательную применимость по HP-RULE-006 и не откладывает связывание до завершения этих проверок. Все последующие сигналы и решения этого дела используют ту же конфигурацию; повторное установление оплаты не перепривязывает дело. Новая конфигурация применяется только к новым допущенным делам после явного момента активации. При совпадении изменения и допуска должно быть однозначно установлено, какая одна версия приняла дело. Принятая конфигурация не изменяется задним числом.

**Исключения:** в определённых профилях HP-CAP-001/004 нет автоматической миграции начатого дела. Дополнение разрешённых данных, смена ответственного и восстановление подключения в пределах той же области не меняют принятую бизнес-политику. Отзыв доступа действует немедленно по HP-POL-001. Состояние/дедупликация не сбрасываются при новой версии. Основание HP-POL-005.

### HP-RULE-005

**Роли и разрешённые действия. Нормативная роль:** общее правило.

| Роль | Разрешённая область |
| --- | --- |
| Владелец workspace/операции | При наличии внешних полномочий подключает/отзывает доступ, принимает конфигурацию и изменения, назначает операторов, управляет паузой/архивом, закрывает без подтверждения и возобновляет такие дела |
| Оператор дела | Видит разрешённые ему дела, дополняет разрешённый контекст, проверяет и связывает существующую задачу, инициирует предусмотренное безопасное продолжение. Не изменяет правило, подключение, платёжный факт или область полномочий |
| Читатель | Видит разрешённую область и доказательства в доступных пределах; не меняет дела и конфигурацию |
| Уполномоченная поддержка HitPipe | Диагностирует и помогает только в явно разрешённой области; не приобретает бизнес-полномочия автоматически |

**Правило:** каждое изменение имеет реального инициатора и проверяемую область. Наличие ссылки, AI-ответа или внешнего task ID не даёт прав. Создание workspace и назначение первого владельца должны установить одного действительного ответственного до первой активации. Для MVP допустима явно описанная управляемая подготовка workspace сервисом с подтверждением владельца; скрытые постоянные ручные операции не подменяют продукт.

**Исключения:** роли могут совмещаться; обязательные внешние ограничения и HP-POL-001/003 сохраняются. Назначение оператора не равнозначно передаче полномочий внешнего аккаунта. Независимые проверки изоляции и аудита принадлежат NFR.

### HP-RULE-006

**Допустимость первого pack. Нормативная роль:** продуктовое правило HP-PACK-001.

**Допустимый заказ:** Checkout Session из выбранного подтверждённого Stripe account и выбранного test/live-контекста; mode=payment; установленная полная оплата со статусом paid; положительная итоговая сумма; одна единица одного заранее настроенного фиксированного Price/service package. В связанном платеже подтверждены успешное получение полной итоговой суммы в той же валюте, отсутствие любого уже выполненного возврата и отсутствие dispute. Нужный контекст и назначение задаёт принятая конфигурация. Перед созданием задачи эти обязательные платёжные признаки и принадлежность проверяются по доступному состоянию источника; неизвестный, недоступный либо противоречивый признак удерживает действие. Факт проверки и её время сохраняются. Последующее изменение платежа после этой проверки не покрывается обещанием атомарной неизменности между сервисами.

**Начальная область времени:** поддерживаются Session, созданные не ранее явно показанного момента первой активации операции. Это ограничивает исторический импорт. Session, созданная раньше границы, получает понятную причину исключения; позднее получение сигнала не отменяет границу. Смена версии не сдвигает исходную границу и не включает старые заказы автоматически.

**Не входят:** subscription/setup, zero-value/no_payment_required, частичная/неустановленная оплата, неподходящий состав заказа, возврат/отмена до проверки, чужой аккаунт и смешение test/live. Истечение checkout или unpaid completion не считается платёжным допуском. Такой сигнал не закрепляет вечное исключение бизнес-объекта: последующий фактически paid-сигнал той же Session заново оценивается по тем же границам. Несколько событий не создают несколько дел.

**Граница сопровождения:** возвраты, dispute, продления, физическое исполнение и отмена после подтверждённого handoff не выполняются автоматически. Новый доступный факт о несоответствии отражается по HP-RULE-002/009; автоматической финансовой компенсации и удаления задач нет.

**Основания:** HP-VIS-D-004; документированные свойства источника HP-DA-S-035/036/050/051. Ограничение первой формы и времени — самостоятельный продуктовый выбор. Точные endpoint/schema specifications не задаются.

### HP-RULE-007

**Целевой результат и предел подтверждения. Нормативная роль:** продуктовое правило.

**Применимость:** HP-PACK-001, создание или связывание задачи.

**Правило:** подтверждённый результат — одна доступная связанная ClickUp task в принятом List, с согласованным исполнителем, названием выбранной услуги/заказа, однозначной ссылкой/маркером исходного дела и всеми обязательными полями контекста принятой конфигурации. Нормативные поля берутся из проверяемых стандартных полей задачи и её описания; обязательная поддержка платных custom-field возможностей не предполагается. Владелец заранее видит точный набор необходимых полей. Недостающие данные не домысливаются.

Подтверждение основано на чтении назначения и сравнении согласованных атрибутов; сохраняются фактические наблюдённые значения, источник и момент проверки. Несколько подходящих задач не являются достаточной однозначной связью. Доступ к задаче без права проверить существенный атрибут оставляет соответствующий результат неподтверждённым.

**Исключения:** успешная отправка, task ID или ручная отметка «готово» без указанной проверки не подтверждают этот результат. Проверка подтверждает handoff на момент чтения; непрерывный мониторинг существования задачи или исполнения услуги не входит автоматически. Расхождение после прежнего подтверждения не переписывает прошлый факт и не разрешает автоматическое повторное создание. Основание HP-POL-002, HP-VIS-D-005.

### HP-RULE-008

**Повтор и неизвестный внешний эффект. Нормативная роль:** общий инвариант.

**Правило:** перед дополнительным созданием должно быть достаточно установлено, что прежний эффект не мог возникнуть, либо внешний контракт действительно обеспечивает безопасное повторение именно данного эффекта. При неизвестном исходе отправленной записи дополнительное создание автоматически запрещено. Пустой/неполный поиск, timeout, истечение срока или мнение AI достаточным основанием не являются. Повторные сигналы и одновременные команды восстановления не разрешают конкурентные дополнительные записи того же дела.

В выбранном первом pack неизвестный эффект разрешается проверкой/связыванием существующей задачи, достоверным установлением исхода либо закрытием без подтверждения. Интерфейс не предлагает оператору «всё равно создать ещё одну» как обход. При установленном отказе до эффекта допустима ограниченная повторная попытка по той же принятой конфигурации после устранения причины. Бюджеты/время попыток — HP-NFR-003/004.

**Исключения:** намеренное создание новой задачи взамен удалённой и финансовая компенсация не включены в определённые профили. Изменение этой границы требует нового явного продуктового поведения, а не ручного сброса кейса. Основания HP-POL-001/002/004/005, HP-RULE-001.

### HP-RULE-009

**Причины, новые факты и границы наблюдения. Нормативная роль:** общее правило.

Причина исключения/ожидания/ошибки указывает объект, установленное, неизвестное и доступное действие. Новый платёжный/целевой факт присоединяется к тому же делу. Если факт противоречит требуемому условию до действия, затронутое действие удерживается. Если после ранее подтверждённого handoff обнаружено удаление/изменение назначения или возврат, история сохраняет прежнюю проверку, а текущее наблюдение показывается отдельно и при необходимости требует внимания. Автоматического удаления, восстановления task или отмены услуги нет. Продукт явно различает последнее подтверждение и текущую непроверенность; мониторинг не подразумевается отсутствием нового сообщения.

**Основание:** HP-POL-002/005. Сценарии и видимость — HP-CAP-002/003; качество понятности — NFR.

### HP-RULE-010

**Непрерывная ответственность. Нормативная роль:** общее правило.

Каждое дело с момента допуска имеет действительного ответственного: по умолчанию владельца операции. Назначение оператору допустимо только в его разрешённой области. Уход/отзыв оператора возвращает ответственность действительному владельцу; удаление последнего владельца активной/незавершённой операции запрещено до передачи ответственности. Недоступность человека не превращает ожидание в подтверждение или автоматическое рискованное действие. Все незавершённые дела остаются видимыми ответственному, включая приостановленные и закрытые без подтверждения с сохранённой неизвестностью.

**Исключения:** дополнительных обходов нет; невозможность связаться с владельцем показывается как операционное препятствие и не скрывает дела. Основания HP-POL-005, HP-VIS-D-001/003.

### HP-RULE-011

**Область подключений и единственный маршрут. Нормативная роль:** общее правило.

Принимаемая конфигурация именует один Stripe account, один test/live-контекст и один ClickUp Workspace/List с допустимым исполнителем. Действия не перенаправляются в другой аккаунт/список автоматически при сбое. Один и тот же исходный account/context допускается для данного pack в одном workspace HitPipe; попытка второго подключения требует устранения конфликта уполномоченным владельцем без раскрытия чужих данных. Это не запрещает сторонние автоматизации клиента, но их возможные записи и область ответственности должны быть явно указаны при настройке.

Для профиля HP-CAP-004/PROFILE/SINGLE в workspace действует одна активная операция HP-PACK-001. Для HP-CAP-004/PROFILE/TEAM несколько операций допустимы только по HP-RULE-014. Восстановление подключения должно сохранять ту же внешнюю идентичность и область; смена назначения создаёт новую принятую конфигурацию.

**Основания:** HP-POL-001/003/005; ограничение первой версии — осознанный продуктовый выбор, не техническая архитектура.

### HP-RULE-012

**Источники данных и разрешённые дополнения. Нормативная роль:** общее правило.

Платёжный факт, исходная identity, сумма, валюта, состав заказа и test/live относятся к подтверждаемым сведениям источника и не редактируются оператором как способ допуска. Оператор дополняет только заранее определённые поля делового контекста: контакт, краткий бриф и данные, перечисленные в конфигурации. Происхождение и автор дополнения сохраняются. Невалидный/недостаточный ввод не превращается в успешный результат. Уточнение не меняет адресата, услугу или бизнес-политику исходного дела.

Секреты и данные реальных заказов не требуются в AI-диалоге подготовки: используются конфигурация, описание поля и синтетические примеры. Обязательные пределы передачи данных AI определяются HP-POL-003 и HP-NFR-007. Основание HP-POL-001/004/005.

### HP-RULE-013

**Закрытие без подтверждения и возобновление. Нормативная роль:** общее правило.

Только владелец может явно закрыть незавершённое дело без подтверждения, указав причину и приняв показанные пределы знания. Дело получает состояние «Закрыто без подтверждения»; последняя неопределённость, попытки, связь и ответственный остаются доступными. Закрытие не обнуляет identity, не создаёт новый заказ и не разрешает повтор. Дальнейшие сигналы присоединяются к истории; автоматического возобновления записи нет. Владелец может явно возобновить то же дело в допустимом состоянии HP-RULE-002; HP-RULE-008 сохраняется.

**Исключения:** подтверждённый результат устанавливается только HP-RULE-007. Закрытие рабочего случая и уничтожение данных различаются; retention принадлежит NFR. Основание HP-POL-002/005.

### HP-RULE-014

**Маршрутизация нескольких операций. Нормативная роль:** общее правило только при выборе TEAM-профилей.

В одном workspace/source account/context операции HP-PACK-001 имеют непересекающиеся явно выбранные Stripe Price/service identifiers. Активация или изменение не допускаются при пересечении. Один заказ принадлежит одной операции; версия и повтор не меняют это назначение. Если конфликт всё же обнаружен при допуске, ни одна новая внешняя запись по нему не выполняется; конфликт видим владельцу с условием разрешения. Устранение конфликта не перезаписывает уже связанное дело и не создаёт дополнительное действие. Правило не включает несколько аккаунтов, смешанные packs или произвольный приоритет первого совпадения.

**Исключения:** автоматического union, выбора AI или гонки операций нет. Основания HP-RULE-001/004/011, HP-POL-001/002/005.

## 5. Вопросы и проверка

Существенные продуктовые выборы настоящей редакции сделаны явно. Эмпирические HP-DA-Q-001–008 и HP-VIS-U-001–004 сохраняются у своих владельцев. Реальная возможность readback и разрешённого восстановления проверяется до live-допуска; документация API не считается результатом испытаний. Здесь не заявлено выполнение каких-либо продуктовых тестов.

Независимый review должен проверить достижимость каждого состояния, отсутствие обходов неизвестного исхода, непротиворечивость паузы/версий/маршрутов, единственное владение правилами и полное покрытие выбранных версий. Фактические результаты review и исправлений находятся в итоговом пакете, а формальный статус — в процедуре Project OS.
