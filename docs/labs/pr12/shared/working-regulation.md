# Регламент изменений и проверки

MANUAL_LAB_PR12 — прямое учебное поручение Lead. Обычные официальные Project OS Task продолжают требовать свои start/freeze/acceptance; эти карточки их не имитируют. Статусы Candidate нормативных документов не меняются.

На карточку отдельная ветка work/<HIT-key>-<slug>, отдельный PR с ключом, scope, source refs, commands/results и evidence. Три C1/C2/C3 на человека — три разных полезных PR. Требования R2 оформляются отдельным содержательным PR. Изменения общего кода, чужого компонента/lock/source требуют Lead и явной интеграционной карточки. Зависимые PR могут быть stacked с явным base; parent merge не выдумывается, после merge база/CI проверяются реально.

Backlog/Todo — план, In Progress — реальная работа. In Review — агентная часть/PR готова реальному review. Blocked — конкретный внешний blocker с владельцем/следующим действием, не любое ожидание. Done — actual DOD, review и merge, где они нужны. Feature/Epic закрывает Lead по полной матрице, не по числу написанных файлов. AI REVIEW/FORCE не проставляются фиктивно. Offline режим создаёт файл предлагаемых Jira updates; фактический внешний статус остаётся UNKNOWN.

Lead проводит человеческий review/merge и организует оппонирование. Методически необходимые проверки ДРУГИМ студентом не заменяются self-review/вторым агентом/одним Lead для всех. Составлен ring: dk проверяет tp; tp проверяет mg; mg проверяет ds; ds проверяет nb; nb проверяет dk. Это назначение, НЕ свидетельство проведённой проверки. Проверяются ясность требований, clean-room scaffold и контракт/заменяемость модуля; вопросы/результаты/среда/SHA/повторная проверка фиксируются настоящим проверяющим. Проверка своего участка другим и проверка чужого студентом — обе стороны обязательны.

Оппонирование другому проекту идёт по реальному кольцу преподавателя: Lead получает назначение/организует, студент сохраняет свои замечания и обработку полученных. До назначения BLOCKED_HUMAN; не подставлять один из пяти модулей того же проекта как другой проект.

Проверки: actual местный запуск + CI на сдаваемой версии; содержательные assertions, нормальный/ошибочный/граничный исход, coverage с разбором, минимум пять отдельно компилируемых поведенческих мутаций, улучшение missed tests, восстановление clean PASS. Отдельный локальный negative gate эксперимент тем же CI-check. Фиксировать реальные команды/cwd/версии/дату/exit/SHA/URL, не выводить PASS из зелёного bootstrap job. Никаких реальных secrets/PII/персональных fixtures. Мутанты не мерджатся.

Main: backend — обязательные PR, независимый human approval, checks и запрет force/delete; readback в readiness.json. Frontend private: GitHub сообщил HTTP403 о недоступности branch protection на текущем тарифе. До снятия ограничения это BLOCKED_HUMAN_GITHUB_PLAN, а не protected main. Lead-only merge policy временная организационная мера, она не подменяет технический критерий методички. Не менять privacy и не оплачивать тариф без решения владельца.

Каждый report/evidence фиксирует version; теги 0104/0302-pz01/pz02-<code>-v1 после actual merge/check неизменяемы, исправления v2. Аннотированный tag указывает submitted SHA; внешняя submission record фиксирует tag→SHA→CI→reports hashes. Подписи/оценки/личную защиту не заполнять за человека.
