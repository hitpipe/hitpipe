ВВЕДЕНИЕ
Практическая работа № 2. Проектирование и реализация системы проверок программного продукта.
Компетенции: работа формирует ПК 4.2, ПК 4.4 (анализ рисков), ОК 01, ОК 02, ОК 03. Прямое подтверждение ПК 4.2 — измерение эксплуатационных характеристик в практической работе №6, ПК 4.4 — защитная мера в практической работе №7; результаты настоящей работы учитываются в текущем контроле.
Форма: работа выполняется индивидуально на объекте из зоны ответственности студента в общем проекте. Отчёт оформляется по шаблону, защита и отметка индивидуальные.
Учебный пример отчёта VKP приведён в приложении А.
1 Цель и задачи работы
Цель работы — формирование умений проектировать, реализовывать и анализировать систему проверок программного модуля на основе требований и рисков.
Задачи работы:
1) Сформулировать проверяемые правила поведения программного модуля на основе требований.
2) Спроектировать набор проверок с применением техник тест-дизайна.
3) Подготовить воспроизводимые тестовые данные.
4) Реализовать автоматические тесты и выполнить их в локальной среде и в конвейере непрерывной интеграции.
5) Проанализировать покрытие кода тестами.
6) Оценить способность набора проверок обнаруживать дефекты на серии засеянных дефектов.
7) Составить реестр рисков объекта и определить приоритеты проверок по матрице «вероятность × ущерб».
2 Теоретические сведения
2.1 Основные понятия
Таблица 1 — Термин / Определение
| Термин | Определение |
| Тест-кейс | Воспроизводимая проверка: исходное состояние, входные данные, действия и ожидаемый результат |
| Тестовый оракул | Источник ожидаемого результата: требование, независимый расчёт или согласованный эталон |
| Класс эквивалентности | Множество входных значений, для которых программа должна вести себя одинаково |
| Граничное значение | Значение на границе класса эквивалентности или непосредственно за ней |
| Заглушка (stub, mock) | Контролируемая замена зависимости, недоступной или неудобной при тестировании |
| Покрытие кода | Доля элементов кода (строк, ветвей), выполненных при прогоне тестов |
| Искусственный дефект (мутация) | Преднамеренное изменение кода, нарушающее требование, для оценки чувствительности тестов |


2.2 Проектирование проверок на основе требований
Проверки выводятся из требований, а не подбираются произвольно. Порядок вывода рассмотрим на примере требования: «при сумме заказа от 1000 рублей предоставляется скидка 10 %; отрицательная сумма является ошибкой ввода».
Сначала требование записывается как проверяемое правило — так, чтобы для любого входного значения из него однозначно следовал ожидаемый результат. Затем множество входных значений разбивается на классы эквивалентности. В примере их три: сумма от 0 до 999 (скидка не предоставляется), сумма от 1000 (скидка предоставляется) и отрицательная сумма (ошибка). Из каждого класса достаточно одного представителя, поскольку внутри класса программа ведёт себя одинаково.
Далее к представителям классов добавляются граничные значения. Ошибки в программах чаще всего возникают на границах условий, например при использовании операции > вместо >=. В примере граница проходит между значениями 999 и 1000.
Для каждого выбранного значения ожидаемый результат определяется по требованию. Получение ожидаемого результата запуском проверяемой программы недопустимо: в этом случае тест подтверждает любую, в том числе ошибочную, реализацию.
Таблица 2 — Входное значение / Ожидаемый результат
| Входное значение | Ожидаемый результат | Основание выбора |
| 500 | Скидка не предоставляется | Класс «от 0 до 999» |
| 1500 | Скидка 150 рублей | Класс «от 1000» |
| −1 | Ошибка ввода | Класс «отрицательная сумма» |
| 999 | Скидка не предоставляется | Граница, последнее значение без скидки |
| 1000 | Скидка 100 рублей | Граница, первое значение со скидкой |


Таким образом, пять проверок, каждая из которых обоснована, проверяют требование полнее, чем произвольный набор большего объёма. Если требование сочетает несколько условий, применяется таблица решений; если объект изменяет своё состояние в ответ на события — техника переходов состояний. Подробно техники рассмотрены в лекции 10.
2.3 Оценка набора проверок
Успешное выполнение тестов само по себе не доказывает их достаточность. Для оценки набора используются два способа.
Анализ покрытия показывает, какие участки кода не выполнялись при тестировании. Невыполненный участок либо требует дополнительной проверки, либо должен быть обоснованно исключён. Процент покрытия не является самостоятельным показателем качества: полностью выполненный код может проверяться тестами без содержательных утверждений.
Засев искусственных дефектов показывает, обнаруживает ли набор нарушения требований. В код поочерёдно вносятся ошибки, например изменяется условие на границе, после каждой выполняются те же тесты. Набор обнаружил дефект, если хотя бы один тест завершается с ошибкой по причине нарушения требования. Доля обнаруженных засеянных дефектов характеризует чувствительность набора; вместе с числом естественных дефектов, найденных при разработке тестов, она используется для статистической оценки остаточной дефектности по Миллсу (теоретическое занятие о классификации дефектов).
2.4 Риск-ориентированный подход
Риск характеризуется вероятностью нежелательного события и тяжестью его последствий. Риски объекта записываются в реестр рисков, приоритет определяется по матрице «вероятность × ущерб».
Таблица 3 — Вероятность \ Ущерб / Небольшой
| Вероятность \ Ущерб | Небольшой | Значимый | Тяжёлый |
| Низкая | Низкий | Средний | Высокий |
| Средняя | Средний | Высокий | Высокий |
| Высокая | Средний | Высокий | Высокий |


Проверки рисков высокого приоритета выполняются при каждом изменении кода; проверки, требующие реальной среды, могут выполняться реже, что фиксируется в отчёте.
Реестр рисков содержит для каждого риска: идентификатор, нежелательное событие, причину, последствие, вероятность, ущерб, приоритет, связанную проверку и решение (проверка при каждом изменении, ручная проверка, отложено с причиной). В реестр включаются риски нарушения требований и не менее одного риска безопасности: недоверенный ввод, доступ к существенному действию, раскрытие данных или секретов.
3 Объект работы
Объектом работы является программный модуль, класс или функция из зоны ответственности студента, реализующие существенное правило продукта. Объект должен иметь определённые входные данные, результат и ошибочные ситуации и допускать вызов отдельно от остальной системы. Готовность основного пользовательского сценария продукта не требуется.
Таблица 4 — Тип продукта / Пример объекта работы
| Тип продукта | Пример объекта работы |
| Веб-сервис | Проверка прав доступа, правило бронирования или расчёта |
| Настольное приложение | Проверка пересечения записей, импорт файла |
| Мобильное приложение | Расчёт, проверка полей формы, правило скидки |
| Игра | Смена состояний персонажа, правило начисления урона или очков |
| Система телеметрии | Разбор пакета данных, проверка диапазона значений |
| Интеграция, бот, консольная утилита | Преобразование формата, разбор аргументов |


Если зона ответственности студента относится к пользовательскому интерфейсу, объектом выбирается логика представления: проверка полей формы, форматирование данных, смена состояний экрана. Вёрстка и оформление объектом работы не являются.
Если в зоне ответственности отсутствует подходящий объект, до начала работы с преподавателем согласуется один из вариантов:
1) Выделение в зоне ответственности функции с определёнными входом и результатом без добавления искусственной логики.
2) Выбор другого доступного участка общего продукта.
3) Выполнение работы на копии части кода с подготовленными данными.
4) Использование резервного стенда преподавателя.
Выбранный вариант указывается в отчёте. Тесты функции, отсутствующей в коде, выполнение работы не подтверждают.
При работе нескольких студентов с одним модулем каждый проверяет собственные правила и представляет собственные тесты. Общие средства проекта (тестовый фреймворк, конфигурация непрерывной интеграции, генераторы данных) указываются в отчёте ссылкой с указанием автора. Студент, выполняющий проект один, выполняет работу в том же объёме.
4 Порядок выполнения работы
4.1 Описание объекта и правил
Указываются расположение модуля в репозитории, его входные данные, результат и возможные ошибки. Выписываются требования спецификации, относящиеся к объекту, и формулируются проверяемые правила в соответствии с п. 2.2. Неточное требование уточняется через задачу и запрос на слияние (MR); подгонка требования под текущую реализацию не допускается.
4.2 Проектирование проверок
Для каждого правила по методике п. 2.2 выделяются классы эквивалентности и граничные значения; при необходимости применяются таблица решений или переходы состояний. Применяется не менее двух техник. Набор должен содержать проверку штатного поведения, ошибочного входа и граничного значения. Количество проверок определяется правилами и не нормируется. Составляется краткий перечень проверенных аспектов (чек-лист).
4.3 Подготовка тестовых данных
Тестовые данные размещаются в репозитории: в коде тестов, в файлах или в виде генератора с фиксированным начальным значением. Тесты должны воспроизводиться из чистого клона по команде, указанной в отчёте, без личных файлов и рабочих учётных данных. Использование реальных персональных данных не допускается.
Преподаватель может выдать скрытый набор данных, неизвестный студенту при проектировании. В этом случае проверка выполняется на сдаваемой версии и её результат анализируется в отчёте. До выдачи набора в отчёте указывается «не получен».
4.4 Реализация автоматических тестов
Тесты реализуются средствами тестового фреймворка проекта и должны содержать утверждения о результате. Тест, выполняющий вызов без проверки результата, требование не подтверждает.
Зависимости, недоступные или неустойчивые при тестировании (системное время, сеть, устройство, внешний сервис, ресурсоёмкая модель машинного обучения), заменяются заглушками или записанными ответами, сохранёнными в репозитории. Для каждой замены в отчёте указывается, какое поведение она не проверяет. Например, подставленный в тест список устройств подтверждает правило выбора устройства, но не взаимодействие с драйвером.
Изменения вносятся в соответствии с регламентом проекта: задача, рабочая ветка, запрос на слияние, автоматические проверки, слияние.
4.5 Выполнение тестов
Тесты выполняются в локальной среде и в конвейере непрерывной интеграции для сдаваемой версии. Ошибка теста должна приводить к неуспешному завершению задания конвейера. Результат каждого прогона фиксируется статусом: PASS — фактический результат совпадает с ожидаемым; FAIL — не совпадает, причина подлежит анализу; BLOCKED — выполнению препятствует среда; NOT RUN — проверка не выполнялась. Успешным считается только статус PASS.
Результаты фиксируются снимками экрана (рисунки 1 и 2 отчёта), на которых видны версия, наименования тестов студента и итог выполнения.
Если выполнение тестов в конвейере невозможно по объективной причине (лицензия игрового движка, эмулятор, специальное оборудование), по согласованию с преподавателем проверяемая логика выносится в часть, тестируемую без этой среды, и её тесты выполняются в конвейере. Остальные тесты выполняются локально на той же версии с сохранением полного журнала. Отсутствие настроенного конвейера объективной причиной не является.

4.6 Анализ покрытия
Строится отчёт покрытия для модуля студента. Выявляется участок кода, не выполнявшийся при тестировании, и принимается решение: дополнить набор тестом, обоснованно отложить проверку или обосновать её ненужность. Если выполнялся весь код модуля, указывается, какие свойства поведения тесты тем не менее не проверяют. Отчёт покрытия фиксируется снимком экрана (рисунок 3).
4.7 Засев дефектов и проверка чувствительности тестов
Эксперимент выполняется во временной ветке в следующем порядке:
1) Тесты выполняются на исправном коде; все тесты должны завершиться успешно.
2) Составляется список не менее чем из пяти дефектов, каждый из которых нарушает проверяемое правило: замена операции сравнения на границе, пропуск проверки ошибочного входа, неверное значение по умолчанию, перестановка ветвей и т. п. Код с каждым дефектом должен компилироваться.
3) Дефекты вносятся по одному. После внесения каждого тесты выполняются повторно, результат записывается в протокол: дефект, нарушаемое правило, тест, завершившийся ошибкой, или «пропущен». Прогон с одним обнаруженным дефектом фиксируется снимком экрана (рисунок 4).
4) Для пропущенного дефекта устанавливается причина; набор дополняется, и прогон с этим дефектом повторяется. В протоколе приводятся результаты обоих прогонов.
5) В протокол вносятся итоги: засеяно, обнаружено, пропущено; число естественных дефектов, найденных набором при разработке тестов, со ссылками на задачи.
6) Все дефекты устраняются, тесты выполняются повторно, результат фиксируется снимком экрана (рисунок 5).
Дефект может быть внесён вручную или средством мутационного тестирования. Ошибка компиляции обнаружением дефекта не считается. Сдаётся исправный код.
4.8 Анализ рисков
Для объекта работы составляется реестр рисков по п. 2.4. Вероятность и ущерб оцениваются качественно (низкая, средняя, высокая) с обоснованием условиями продукта; приоритет определяется по матрице п. 2.4. Используются сведения раннего анализа безопасности практической работы №1. В отчёте указывается, как анализ рисков повлиял на набор проверок: какие проверки выполняются при каждом изменении, какие — вручную, какие отложены и по какой причине.
4.9 Фиксация результата
Сдаваемая версия фиксируется неизменяемым тегом 0302-pz02-<код>-v1, где <код> — короткий идентификатор студента. При доработке создаётся новый тег (0302-pz02-<код>-v2), прежний тег не переносится. Срок сдачи и доработки — по памятке «Индивидуальная работа и сдача». Тесты, данные и отчёты инструментов хранятся в репозитории; в отчёт включаются основные таблицы, снимки экрана и ссылки.

7 Порядок защиты
На защите студент выполняет одно-два действия по выбору преподавателя:
1) Обосновать ожидаемый результат выбранного теста.
2) Указать границу класса эквивалентности и предложить дополнительное входное значение.
3) Выполнить тест и пояснить проверяемое им утверждение.
4) Указать, какое поведение не проверяется используемой заглушкой.
5) Внести указанный дефект и показать тест, который его обнаруживает.
6) Обосновать приоритет одного из рисков.
При выполнении действий на защите генеративный ИИ не используется. Если студент не может выполнить действие или объяснить свой результат, работа возвращается на доработку: результат не засчитывается до повторной проверки, при повторной сдаче действие выполняется заново. Доработка выполняется в течение двух недель после возврата работы и представляется новым тегом; оценка после доработки не ограничивается.

3 Ход работы
3.1 Проектирование проверок (Р2)
Правило П1 определяет одну ситуацию — отсутствие переменной.
Для правила П2 входные строки разделены на классы эквивалентности: строка из цифр; строка из букв; пустая строка; строка из цифр с посторонними символами. Из каждого класса выбран один представитель. Строка «1x» выбрана как характерная ошибка разбора, при которой распознаётся начало строки, а посторонние символы в конце не обнаруживаются.
Правило П3 проверяется для двух видеокарт. Допустимые номера — 0 и 1. Применены граничные значения: нижняя граница 0, верхняя допустимая граница 1 и первое недопустимое значение 2.
