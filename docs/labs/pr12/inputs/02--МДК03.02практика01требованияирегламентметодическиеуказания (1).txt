ВВЕДЕНИЕ
Практическая работа № 1. Формирование требований и регламента инженерного процесса проекта.
Компетенции: работа формирует ПК 4.2 (настройка регламента изменений и Quality Gate v0 — принципы контроля конфигурации), ОК 01, ОК 02, ОК 03, ОК 04, ОК 05. Прямым подтверждением ПК работа не является: наличие спецификации или настроенного репозитория само по себе профессиональную компетенцию не подтверждает; результаты работы учитываются в текущем контроле.
Форма: общие документы проекта (устав, протокол обследования, спецификация требований, регламент репозитория) — общие артефакты проекта, в которые каждый студент вносит свою часть с указанием автора; каждый студент выполняет работу на своём участке продукта и оформляет отчёт по шаблону. Защита и отметка индивидуальные.
Учебный пример отчёта VKP приведён в приложении А.
1 Цель и задачи работы
Цель работы — формирование умений выявлять потребности пользователя, формулировать проверяемые требования и организовывать управляемый процесс внесения изменений в программный продукт.
Задачи работы:
1) Провести предпроектное обследование и отделить подтверждённые сведения от предположений.
2) Определить основной сценарий продукта, обязательное ядро (MVP) и резерв функций.
3) Сформулировать функциональные и нефункциональные требования своего участка с критериями приёмки.
4) Определить исходное состояние для будущих проверок и ранние ограничения безопасности.
5) Согласовать критерии готовности изменения (DoD) и внести значимое изменение по регламенту репозитория.
6) Провести оппонирование требований другого проекта и принять решения по замечаниям к своим требованиям.
2 Теоретические сведения
2.1 Основные понятия
Таблица 1 — Термин / Определение
| Термин | Определение |
| Требование | Ожидаемое поведение или свойство продукта |
| Функциональное требование (FR) | Требование к действию продукта: что он делает в заданных условиях |
| Нефункциональное требование (NFR) | Требование к свойству продукта: быстродействию, надёжности, переносимости и т. п. |
| Критерий приёмки | Условие, по которому однозначно устанавливается выполнение требования |
| MVP | Минимальное работающее ядро продукта, выполняющее основной сценарий |
| Baseline | Зафиксированная версия требований и состава MVP, относительно которой рассматриваются изменения |
| Definition of Done (DoD) | Перечень условий, при выполнении которых изменение считается готовым |
| Запрос на слияние (MR, PR) | Предложение включить изменение из рабочей ветки в основную |
| Quality Gate v0 | Начальные правила допуска изменения: назначение, применимые автоматические проверки, независимая проверка значимых изменений |
| Значимое изменение | Изменение контракта, архитектуры, существенных требований, схемы данных, сборки или поставки, исправление критичного дефекта, программная защитная мера |


2.2 Проверяемое требование
Требование считается проверяемым, если другой человек по его тексту может определить ожидаемый результат и способ проверки без пояснений автора. Формулировки «удобный интерфейс», «быстро обрабатывает», «надёжная система» не являются проверяемыми. Например, требование «быстро обрабатывает данные» уточняется указанием объёма и структуры входных данных, среды, измеряемой величины и допустимого значения.
Функциональное требование удобно записывать в форме «Дано — Когда — Тогда»:
Дано: интервал уже занят активной записью. Когда: поступает новая заявка на тот же интервал. Тогда: вторая запись не создаётся, пользователь получает сообщение об отказе, существующая запись сохраняется.
Для каждого существенного действия определяется не только штатный, но и ошибочный исход: поведение продукта при неверных данных, недоступности ресурса или конфликте. Если для продукта существенны одновременные обращения, ожидаемый результат определяется и для них.
2.3 Предпроектное обследование
Цель обследования — установить реальный процесс пользователя, его затруднения и ограничения, а не получить одобрение предложенной идеи. Результаты фиксируются протоколом, в котором разделяются подтверждённые сведения, предположения и открытые вопросы. Неполученный ответ оформляется как открытый вопрос; оформление предполагаемых ответов как проведённого разговора не допускается.
2.4 Управляемый процесс изменения
Изменение продукта проходит цикл: задача → рабочая ветка → изменение → запрос на слияние → применимые автоматические проверки → независимая проверка (review) для значимого изменения → слияние. Для каждого значимого изменения должны быть понятны причина, автор, результат и способ проверки.
Review является инженерной проверкой, а не формальностью. Содержательное замечание указывает проблему, её последствие и способ устранения, например: «В критерии записи не определено поведение при повторном запросе; две реализации могут выполнить требование по-разному». Количество комментариев и одобрений показателем качества не является.
3 Объект работы
Объектом работы является участок продукта, за который отвечает студент: функция или подсистема с собственной логикой (например, выбор устройства, бронирование, загрузка данных, обработка ошибок). Участки разных студентов могут соприкасаться, но требования, решения и изменения каждого должны быть различимы.
Общие документы проекта — устав, протокол обследования, спецификация требований, состав MVP, регламент репозитория — разрабатываются студентами проекта совместно, вклад каждого указывается с автором; в отчёте они приводятся ссылками на зафиксированную версию. Личную часть работы составляют вопросы обследования, требования и критерии своего участка, собственное значимое изменение и участие в оппонировании. Распределение, при котором один студент только проводит обследование, другой только пишет требования, а третий только настраивает репозиторий, не допускается: каждый студент проходит все этапы на своём участке.
Студент, выполняющий проект один, разрабатывает общие документы самостоятельно в сокращённом объёме. Действия, требующие другого студента, — независимую проверку изменения, проверку однозначности требований и оппонирование — для него выполняет студент другого проекта или преподаватель по назначению преподавателя.
Если в проекте нет участка, подходящего для работы, до её начала с преподавателем согласуется другой участок продукта или учебный участок эталонного проекта преподавателя (VKP). Выбранный вариант указывается в отчёте в поле «Вариант выполнения».
4 Порядок выполнения работы
4.1 Устав проекта
Устав — краткое описание проекта в README или отдельном документе репозитория — составляется для проекта в целом; авторы разделов указываются.
Таблица 2 — Раздел устава / Содержание
| Раздел устава | Содержание |
| Пользователь и проблема | Кто решает задачу с помощью продукта; что затруднено сейчас и как задача решается без продукта |
| Ожидаемый результат | Что пользователь сможет сделать с помощью продукта |
| Собственная логика | Два-три правила, проверки или преобразования, реализуемые собственным кодом проекта |
| Модуль для эксперимента и внешний ресурс | Часть продукта, которую можно будет отдельно наблюдать и измерять; используемые файлы, сеть, БД, устройство |
| Ограничения | Срок, доступность данных и среды, опыт студентов проекта, внешние зависимости |


Использование готовых библиотек, фреймворков, движков и СУБД допускается; в уставе показывается, какие решения продукта определяет собственный код проекта. Искусственное усложнение темы ради выполнения требований курса не допускается.
4.2 Предпроектное обследование
Проводится разговор с пользователем или с согласованным с преподавателем представителем заказчика. Каждый студент готовит вопросы по своему участку. Рекомендуемые вопросы:
1) Как задача выполняется в настоящее время?
2) Какие данные поступают и откуда?
3) Какие действия повторяются и где возникают затруднения?
4) Какие ошибки и исключительные ситуации необходимо учитывать?
5) Какие ограничения обязательны (доступ, сроки, устройства, объём данных)?
6) По каким признакам оценивается пригодность результата?
7) Что необходимо в первую очередь, а что можно отложить?
Результаты оформляются протоколом обследования: дата, участники, текущий процесс, подтверждённые потребности, ограничения, предположения, открытые вопросы, принятые решения. Реальные секреты и излишние персональные сведения в репозиторий не включаются.
4.3 Основной сценарий и MVP
Описывается основной сценарий от действия пользователя до полезного результата, включая существенный ошибочный исход. Функции продукта разделяются на обязательное ядро, без которого сценарий не выполняется, и резерв — полезные расширения после работающего ядра. Объём ядра должен быть выполним студентами проекта с учётом учебной нагрузки. Студент указывает место своего участка в сценарии и в составе MVP.
Перенос функции между ядром и резервом в дальнейшем оформляется явным решением (ADR или запрос на изменение требований, CR). Исключение обязательной функции без такого решения не допускается.
4.4 Регламент изменений и DoD
Для проекта настраивается репозиторий; изменения настроек вносятся с указанием автора: защищённая основная ветка, работа через запросы на слияние, применимые автоматические проверки, обязательная независимая проверка значимых изменений. Минимальный исполняемый компонент, созданный в МДК.01.04, вносится в основную ветку тем же порядком.
Студенты проекта согласуют DoD; в одиночном проекте студент составляет его сам. Типовой состав:
1) Понятно, какую задачу или требование решает изменение.
2) Выполнены применимые проверки, их результаты доступны.
3) Для изменения наблюдаемого поведения указан способ его проверки.
4) Обновлены затронутые инструкции, конфигурация или требования.
5) В код и диагностическую выдачу не добавлены секреты.
6) Значимое изменение прошло независимую проверку, существенные замечания разрешены.
Quality Gate v0 не требует полного набора тестов и анализаторов: сборка и простые проверки добавляются по мере появления кода. В отчёте указывается фактический состав проверок. Конвейер, не выполняющий никаких проверок, Quality Gate не подтверждает.
4.5 Требования своего участка
Студент формулирует требования своего участка для спецификации 1.0:
1) Функциональное требование к штатному поведению.
2) Существенный ошибочный исход (отдельным требованием или подпунктом того же требования).
3) Значимое нефункциональное требование с измеримым критерием.
Каждому требованию присваивается идентификатор (FR-01, NFR-01 и т. п.), указываются основание (результат обследования, ограничение), принадлежность к MVP или резерву и критерий приёмки. Числовые значения нефункциональных требований на данном этапе являются целями, а не подтверждёнными характеристиками продукта; уже доступное поведение отличается от планируемого.
4.6 Исходное состояние и ранние ограничения безопасности
Для своего участка указывается, как проверяющий получит состояние, необходимое для будущих проверок: примеры входных данных, учебные учётные записи, конфигурация, способ генерации данных. Если продукт обращается к внешней системе, предусматривается учебный режим, не зависящий от личных доступов разработчика.
Для оценки ранних ограничений безопасности даются ответы на вопросы:
1) Какие данные или ресурсы участка необходимо защищать?
2) Откуда поступает недоверенный ввод?
3) Кто должен иметь доступ к существенным действиям?
4) Какой ущерб реалистичен при ошибке или злоупотреблении?
5) Где хранятся секреты и что нельзя выводить в журнал?
Полная модель угроз и реализация защитных мер выполняются в последующих работах.
4.7 Значимое изменение по регламенту
Студент вносит собственное значимое изменение — например, уточнение требования своего участка — по регламенту: задача, рабочая ветка, запрос на слияние, применимые проверки, независимая проверка другим студентом проекта (в одиночном проекте — студентом другого проекта или преподавателем), слияние. В отчёте показывается применение DoD к этому изменению. Задача и запрос на слияние приводятся ссылками и фиксируются снимком экрана (рисунок 1), результат автоматических проверок — ссылкой и снимком экрана (рисунок 2).
4.8 Проверка однозначности требований
Другой студент проекта (в одиночном проекте — студент другого проекта или преподаватель) по тексту требований участка определяет ожидаемые исходы для нескольких ситуаций, включая ошибочную. Совпадение его ответов с замыслом автора подтверждает однозначность формулировок; расхождение указывает на необходимость уточнения. Результат фиксируется в отчёте.
4.9 Оппонирование и фиксация baseline
Спецификация 1.0 предъявляется студентам другого проекта; проекты проверяют друг друга по кольцу, назначенному преподавателем. Оппоненты устанавливают, понятны ли пользователь и результат, проверяемы ли обязательные требования, выполним ли сценарий в границах MVP, реалистичны ли объём и внешние зависимости, отделены ли подтверждённые сведения от предположений.
Студент разбирает требования другого проекта и принимает решения по замечаниям к требованиям своего участка: «принято», «принято частично», «отклонено» или «требует уточнения» — с обоснованием. Обсуждение одного из замечаний фиксируется снимком экрана (рисунок 3). Искусственное формирование замечаний не требуется.
После обсуждения фиксируется baseline проекта — версия спецификации 1.0 и состава MVP; автор фиксации указывается. Существенная неопределённость, делающая основной сценарий невыполнимым, устраняется до фиксации baseline.
4.10 Фиксация результата
Промежуточный результат (устав, протокол обследования, исходные требования, предварительный MVP, действующий регламент репозитория) предъявляется на контрольной точке КТ-1. Полная сдача работы выполняется после фиксации baseline. Сдаваемая версия фиксируется неизменяемым тегом 0302-pz01-<код>-v1, где <код> — короткий идентификатор студента; при доработке создаётся новый тег (0302-pz01-<код>-v2), прежний тег не переносится. Срок сдачи и доработки — по памятке «Индивидуальная работа и сдача».
5 Содержание отчёта
Отчёт оформляется по шаблону и содержит:
1) Сведения о работе: студент, проект, участок, версия сдачи, вариант выполнения.
2) Цель и задание: участок, его место в сценарии и MVP.
3) Краткое описание проекта со ссылками на общие документы.
4) Ход работы: обследование по участку, требования участка, исходное состояние и ограничения безопасности, значимое изменение по регламенту, оппонирование.
5) Результаты: проверка однозначности требований, результаты проверок изменения.
6) Заключение.
7) Список использованных материалов.

7 Порядок защиты
На защите студент выполняет одно-два действия по выбору преподавателя:
1) Обосновать существование проблемы пользователя сведениями обследования.
2) Указать предположение, требующее проверки.
3) Переформулировать нечёткое требование в проверяемое.
4) Указать функцию, которую можно перенести в резерв без потери основного сценария.
5) Показать путь своего изменения от задачи до слияния и пояснить применение DoD.
6) Обосновать решение по одному из замечаний оппонентов.
При выполнении действий на защите генеративный ИИ не используется. Если студент не может выполнить действие или объяснить свой результат, работа возвращается на доработку: результат не засчитывается до повторной проверки, при повторной сдаче действие выполняется заново. Доработка выполняется в течение двух недель после возврата работы и представляется новым тегом; оценка после доработки не ограничивается.
