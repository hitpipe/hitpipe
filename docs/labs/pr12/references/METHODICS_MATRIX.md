## Правила доказательств и инструментов

- Тесты и данные должны существовать; ни один тест функции, которой нет в коде, не подтверждает работу. UX выполняет логику формы/представления/переходов, а не только оформление.
- ≥5 мутаций на каждого: код компилируется, дефект нарушает правило, один мутант за раз. Нет искусственного требования «обязательно иметь пропуск» или «обязательно найти естественный дефект»; нули допустимы с фактическим протоколом.
- Минимум2 техники тест-дизайна; количество тестов в МДК03.02 ПР2 не нормируется. Для подмены МДК01.04 ПР2 штатный/граница/ошибка должны реально исполняться с каждой из2реализаций.
- Метрика покрытия — область+вид+команда+пробел+решение, не произвольный порог90%. Даже100% не доказывает семантическую полноту.
- Риски оцениваются точной матрицей преподавателя, а не умножением произвольных баллов. Низкая×тяжёлый уже высокий, высокая×небольшой только средний.
- Существующий архитектурный ADR не приписывается студенту; МДК01.04 ПР2 требует его собственное решение о границе с автором/альтернативами/ценой/проверкой.
- Все4 сдаваемых тега студента неизменяемы. Если DOCX в том же commit, SHA и pipeline фиксируются сопровождающей записью после тега; не создавать commit ради записи его собственного SHA.
- Go/Node/Python можно использовать без искусственного усложнения и недоказанных performanceгарантий. Сборочные режимы и средство инспекции выбираются по реальному стеку.
